## 1. 目标与范围

**本模块回答：Agent 的能力边界怎么从「内置」变成「开放生态」？**

- **MCP**：标准协议接入外部工具（USB 类比：M×N 对接 → M+N），第三方独立开发 Server、零代码接入。落地 Host/Client/Server 三角色 + Data/Transport 两层。
- **Skill**：把可复用流程封装成「写给 Agent 的 SOP」，Markdown 定义（frontmatter + body），两阶段加载 + 意图识别，解决「重复解释 / 大文件无差别加载 / 团队知识流失」三痛点。
- **两者关系**：Function Calling 负责调用、MCP 负责接入、Skill 负责编排——一个 Skill 可以调用 MCP 工具完成整条工作流。

**不在本模块范围**：
- 内置工具本体与 Tool 协议 → `03`（本模块用 wrapper 适配、registry 扩展）
- 权限裁决与 Hook 拦截 → `06`（本模块只定义 MCP 工具命名约定供规则匹配）
- Skill 的 fork 独立上下文运行时 → `10` SubAgent（好用档降级方案见 §3.9）
- MCP Resources / Prompts 的完整 wrapper → 生产级（好用档只做 Tools，见 §3.10 与 T23）

```
   02 ReAct Loop ──► ToolSearch（拉取延迟工具）/ LoadSkill（读 SOP）──► 03 工具系统
        │
   06 权限规则 ◄── mcp_<server>_<tool> 命名匹配
   05 CommandRegistry ◄── Skill 自动注册为 /name；补 /mcp /skills
```

- **消费 `03`**：`MCPToolWrapper` 实现 `Tool` 协议后注册进 `ToolRegistry`（03 §3.4 已预留扩展点：wrapper 适配 + 延迟加载走注册表）。
- **消费 `01`**：`assemble_payload` 已预留「可用 Skill」「已连接 MCP Server」system-reminder 槽位（01 §3，第 96-108 行），本模块填入内容；延迟工具的名字列表也走 system-reminder，**不改 system 字段 → 前缀缓存不受影响**。

- **消费 `06`**：MCP 工具命名 `mcp_<server>_<tool>`，天然可被权限规则（`ToolName(pattern)`）匹配。
- **为 `10`**：Skill fork 模式复用 SubAgent 独立上下文；为 `12`：Skill/MCP 命中率、工具准确率是评估数据点。

## 3. 详细设计

### 3.1 MCP 概览：三角色 + 两层

```
KDAgent（Host）
   ├── MCP Client A ──stdio──► GitHub Server（npx 子进程）
   ├── MCP Client B ──stdio──► SQLite Server
   └── MCP Client C ──HTTP──► 远程 Server（Streamable HTTP，预留）
```

- **角色**：Host = KDAgent 本体；Client = Host 内负责连接单个 Server 的组件（一个 Server 一个 Client，各自能力协商/请求 id/连接状态独立）；Server = 能力提供方（本地子进程或远端服务）。
- **两层**：Data Layer（JSON-RPC 2.0 语义：initialize 握手、tools/list、tools/call）+ Transport Layer（消息怎么传：stdio / Streamable HTTP）。transport 只负责收发，上层的会话流程完全不感知管道还是 HTTP。

### 3.2 配置：`mcp_servers` 段（并入主 config）

与 `06` 权限规则三文件模式同构：**用户级 `~/.kdagent/config.yaml` + 项目级 `{work_dir}/.kdagent/config.yaml`**，项目级覆盖用户级同名 Server；`${ENV}` 注入密钥（Token 不进配置文件明文）。

```yaml
# config.yaml 的 mcp_servers 段
mcp_servers:
  github:                      # stdio：有 command 字段 → 启动子进程走管道
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_TOKEN: "${GITHUB_TOKEN}"
  db:                          # Streamable HTTP：有 url 字段 → 发 HTTP 请求
    url: "http://localhost:8000/mcp"
    headers:
      Authorization: "Bearer ${DB_TOKEN}"
```

### 3.3 MCPManager：连接生命周期

**启动即后台连接**（MewCode/Claude Code 同策略）：MCP 要求 tools/list 才能拿工具定义，而 tools/list 必须在连接后——懒连接到调用时才连会造成「Agent 不知道工具存在 → 不调用 → 永不连接」的死循环。所以**启动时异步连接全部 Server**，工具列表注册进 registry，第一轮就能看到。

```
setupMCP(config, registry):
    manager = MCPManager(); manager.load_configs(config)
    err = manager.connect_and_register_all(registry)
    if err: log.warn("部分 MCP Server 连接失败，不阻止启动")   # Token 过期不影响其他 Server
    return manager
```

**单 Server 生命周期**：启动子进程/连接 HTTP → `initialize` 握手（身份 + 能力协商 + 协议版本）→ `notifications/initialized` → `tools/list` 拿工具定义 → 包装注册 → 后续 `tools/call`×N（连接缓存复用，不重复握手）。

**stdio 三通道纪律**：stdin/stdout 只走 JSON-RPC（换行分隔的 UTF-8 JSON）；**stderr 走日志与调试**，不参与协议——Server 开发者随便往 stderr 打日志不干扰通信。**请求-响应异步匹配**：pending map 按 id 分发（Server 可能乱序回复），读取循环从 stdout 持续读；读循环退出 = Server 退出 → `alive=False` 供重连判断。

### 3.4 MCPToolWrapper：适配内部 Tool 接口

MCP 工具定义（name/description/inputSchema）与内部 `Tool` 协议结构对得上（03 §3.2），适配器只做命名 + 透传 + 结果转换：

```python
# tools/mcp/wrapper.py
class MCPToolWrapper(Tool):
    """把 MCP 工具适配为内部 Tool，对 Agent 完全透明。"""

    name: str            # mcp_<server>_<tool>：不同 Server 可能同名工具，前缀防冲突
    description: str     # 透传 toolDef.description
    input_schema: dict   # 透传 toolDef.inputSchema

    def is_read_only(self) -> bool: return False      # MCP 无可靠静态只读标记，保守声明
    def is_concurrency_safe(self, input) -> bool: return False   # 保守声明（外部进程不确定）
    def validate_input(self, input) -> list[str]: return []      # 由 Server 侧校验，本地不透传约束

    async def execute(self, ctx, input) -> ToolResult:
        result = await client.call_tool(toolDef.name, input)   # tools/call
        return ToolResult(name=self.name, content=extract_text(result), is_error=result.is_error)
```

- **extract_text**：从返回的 `content` 块数组提取全部 text 块拼接；`isError` → `ToolResult(is_error=True)`。
- **元信息保守声明**（非只读/非并发安全）：MCP 工具没有静态只读标记，宁可先问也不裸放；用户用权限规则放行可信 Server 的读操作（§3.6）。增强项：若 SDK 暴露 `tool.annotations`（readOnlyHint/destructiveHint），透传以精细声明。
- **结果入口**：包装后走 `03` 同一执行路径（`02._exec_one`）→ 结果进 `01` 入口处理 → `07` tool.exec span 天然覆盖。

### 3.5 工具延迟加载（T21 已决）

**问题**：用户配置 4 个 Server × 15 工具 + 内置 = 80 个工具，每个 schema 100-300 token → 每轮多带 8,000-24,000 token；更重要的是模型在几十个相似工具里选，准确率崩。Anthropic 官方量化：50+ 工具场景延迟加载后 token 开销降约 85%、Opus 4 选择准确率 49% → 74%。

**分界**：**内置工具一律常驻**（数量可控、ReadFile/Bash 几乎每轮用）；**MCP 工具一律延迟**（数量由配置决定、大部分本轮用不上）。这条线划的是「数量可不可控」。

**机制四步**（客户端自实现，不依赖厂商 `defer_loading` 专有字段——GLM/GPT 不支持，跨厂商唯一方案）：

```
buildToolList(registry):
    tools, deferred_names = [], []
    for tool in registry.all():
        if tool.should_defer() and not registry.is_discovered(tool.name):
            deferred_names.append(tool.name)         # 只记名字
        else:
            tools.append(tool.full_schema())         # 完整 schema
    if deferred_names:
        system_reminder += "<system-reminder>\n以下工具可通过 ToolSearch 加载：\n" + join(deferred_names, "\n") + "\n</system-reminder>"
    return tools
```

**ToolSearch**（新内置工具，常驻，readonly，走权限 allow）：
- `select:mcp_github_search_issues` → 按名精确拉取（模型已知道用哪个）
- 关键词「prometheus」 → 在延迟工具的名称+描述里搜索（模型不确定具体名）
- 命中 → 返回完整 schema + `mark_discovered` → **下一轮进 tools 字段**，Agent 正常调用

**registry 扩展**（03 §3.4 预留，不动 Tool 协议本体）：`should_defer(name)`、`is_discovered(name)`、`mark_discovered(name)`、`deferred_tool_names()`。

**内置工具描述深载**（`12` §3.4 引用）：内置工具默认完整 schema 常驻；个别"重语义"内置工具（如 `12` 的 `TestRunner`——参数/隔离/`TestingEvent` 格式/激活条件很长）可声明 `description_defer=True`——tools 字段只放精简描述（名字 + 一句话），完整语义经 `ToolSearch` 按名拉取。`ToolSearch` 搜索范围扩展为**延迟发现的 MCP 工具 + 声明深载的内置工具**两类；分界仍是"数量可不可控"，深载是描述粒度层，两者正交。

### 3.6 安全

- **纳入权限规则**：MCP 工具名可被 `ToolName(pattern)` 匹配——`mcp_github_*(*)` allow / `mcp_*_delete_*(*)` deny，与内置工具同一套裁决链（`06`）。
- **server 命令白名单留口子**：config 可选 `allowed_commands`（限制可启动的 server 命令），默认不限；高安全团队可开。
- **Prompt 注入**：MCP 工具返回内容属外部文本，进入历史后可能伪装指令——`01` system-reminder 机制已标注来源（01 §4.2）；`08` 静默写提取时同样对 MCP 结果保持警惕（提取指令含甄别要求）。

### 3.7 Skill 定义：写给 Agent 的 SOP

**本质**：把「用户每次重复解释的流程」封装成独立 Markdown 文件，只在需要时加载。指令比人类 SOP 更精确（Agent 只会照字面做）。遵循 Anthropic Agent Skills 开放标准（跨平台复用：Claude.ai / Claude Code / API 共用）。

```markdown
---
name: commit                      # 必填：唯一标识，也是 /commit 命令名（小写字母/数字/连字符）
description: 分析 git diff 并生成规范的 commit   # 必填：/help 展示 + 意图识别
mode: inline                     # inline（默认）| fork（独立上下文，依赖 10）
model:                           # 可选：指定模型；默认沿用主对话模型（见下）
context: full                    # fork 模式生效：full/recent/none
---

# 任务
分析 git 变更并生成 commit。

## 步骤
1. 运行 `git status` 查看变更
2. 运行 `git diff` 查看具体变更
3. 按 type(scope): description 生成 message
4. 用 `git add` 逐个添加文件（不要 git add -A）

## 注意事项
- commit message 用英文，description ≤ 72 字符

$ARGUMENTS                        # 用户参数占位符
```

- **`model` 字段与前缀缓存**：`08` 确立「缓存按模型分」——Skill 指定不同模型会破坏该 Skill 执行会话的缓存命中。**默认沿用主对话模型**；`model` 字段保留给「单次独立任务」（如 fork 模式的客观审查）使用，并作为显式权衡。
- **目录型 Skill**：单文件放不下资源时，Skill 演化成目录 `SKILL.md`（入口）+ `examples/` + `scripts/` 等附属资源，Agent 用既有 `ReadFile`/`Bash` 按需访问（SKILL.md 里声明各文件用途与读取时机）；整套可打包移植、git 分发。

### 3.8 加载与搜索优先级

三级搜索，同名高优先级覆盖低优先级（同 npm 包搜索路径）：

```
1. 项目级：{work_dir}/.kdagent/skills/     # 可提交 git、团队共享
2. 用户级：~/.kdagent/skills/              # 个人通用
3. 内置级：程序包内 skills/                 # 开箱即用
```

### 3.9 触发：显式命令 + 意图识别（两阶段加载）

**第一阶段·轻量注册**（启动时）：扫描三个目录，只加载每个 Skill 的 frontmatter（name/description/mode/model），注入 `01` 已预留的「可用 Skill」system-reminder 槽位，**同时注册为 Slash Command**（复用 `05` CommandRegistry 的 RWLock 动态注册，/help 可见、Tab 补全）。模型平时只见名字+描述，选择压力低。

**第二阶段·按需加载**：两种触发并存，执行流程相同：

- **显式**：用户输入 `/commit` → 命令系统 → 加载 Skill SOP。
- **意图识别**：用户说「帮我提交一下」→ Agent 看到「可用 Skill」清单 → 判断匹配 `commit` → 调用 `LoadSkill("commit")` → 完整 SOP 注入对话 → 下一轮按 SOP 执行。

**LoadSkill**（新内置工具，readonly，与 ReadFile/Grep 同通道**不触发权限确认**）：

```
完整流程：
1. 启动：扫描 Skill 目录，加载 frontmatter（轻量）
2. 注入 messages：system-reminder「可用 Skill」（name + description）
3. 注册命令：/name 显式调用
4. 用户输入 → 5. 意图识别 → 6. LoadSkill(name) → 7. 完整 SOP 注入 → 8. 按 SOP + 既有工具执行
```

### 3.10 执行模式：inline / fork（T22 已决）

| 模式 | 上下文 | 适用 | 好用档落地 |
|---|---|---|---|
| `inline`（默认） | SOP 注入当前对话，共享历史、结果留在历史 | /commit（需知前面改了什么） | ✅ 本模块实现 |
| `fork` | 独立上下文，只回结果摘要到主对话；`context` 控制带入量（full/recent/none） | /review（客观审查不被主对话污染） | ⏳ 依赖 `10`，未落地前**降级 inline + 警告** |

### 3.11 与 Slash Command / MCP / 记忆的边界

| 对比 | 边界 |
|---|---|
| **Skill vs Slash Command** | 确定性操作（local/local-ui）走 Command；需 AI 判断且流程可复用走 Skill。Skill 自动注册为命令，用户无感同一入口。最新 Claude Code 已把两者合并为同一机制，本设计保持两套定义、同一注册表 |
| **Skill vs MCP** | MCP 提供工具（接入），Skill 编排工具（SOP + 上下文控制）；Skill 内可调用 MCP 工具（如 commit Skill 调 GitHub MCP 建 PR） |
| **Skill vs 记忆（08）** | 记忆 = 事实/偏好（自动提取、个人专属、机器生成）；Skill = 可执行 SOP（用户维护、可共享、版本控制）。CLAUDE.md 里的事实性内容 → 记忆；操作流程 → Skill |

**`05` 补注册**：`/mcp`（查看已连接 Server / 工具列表 / 连接状态）、`/skills`（查看已加载 Skill 清单）——查看类命令，与 `/permissions` 同构。

### 3.12 关键参数

| 参数 | 初值 | 含义 |
|---|---|---|
| MCP 连接时机 | 启动后台异步连接 | 部分失败 warn，不阻止启动 |
| MCP 工具命名 | `mcp_<server>_<tool>` | 防冲突 + 权限规则匹配 |
| MCP 工具元信息 | 保守声明（非只读/非并发安全） | annotations 透传为增强 |
| 延迟加载分界 | 内置常驻 / MCP 延迟 | 数量可不可控 |
| ToolSearch | `select:` 精确 / 关键词搜索 | 客户端自实现，跨厂商 |
| Skill 搜索优先级 | 项目 > 用户 > 内置 | 同名覆盖 |
| Skill 清单注入上限 | 100 条 / 8KB | 防挤占工作记忆（远小于 01 预算） |
| LoadSkill | readonly，不触发权限确认 | 与 ReadFile 同通道 |
| Skill 默认模型 | 主对话模型 | 缓存按模型分（08 原则） |

## 5. 验收标准

- [ ] 配置 1 个 stdio MCP Server → 启动后工具以 `mcp_<server>_<tool>` 注册进 registry；`/mcp` 可见连接状态
- [ ] 部分 Server 连接失败（Token 过期等）→ 打 warn、不阻止启动，其余 Server 正常
- [ ] Agent 调用 MCP 工具成功（tools/call → extract_text → 结果回传 → 进历史）
- [ ] 未发现的延迟 MCP 工具只列名字进 system-reminder；`ToolSearch("select:mcp_...")` 拉取后**下一轮**出现在 tools 字段
- [ ] ToolSearch 关键词搜索命中（名称+描述），命中即标记已发现
- [ ] 权限规则 `mcp_github_*(*)` allow / `mcp_*_delete_*(*)` deny 生效（06 裁决链）
- [ ] 项目级/用户级 Skill 目录扫描，frontmatter 注入「可用 Skill」system-reminder，自动注册 `/name` 命令（/help 可见、Tab 补全）
- [ ] 显式 `/commit` 触发 + 自然语言意图触发 LoadSkill 两种路径都成功执行 SOP
- [ ] 目录型 Skill：SKILL.md + 附属资源（Agent 用 ReadFile/Bash 访问）；`$ARGUMENTS` 占位符替换
