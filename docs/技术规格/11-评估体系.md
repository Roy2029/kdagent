## 1. 目标与范围

**本模块回答：我的 Agent 到底行不行？改一处之后是变好了还是变坏了？**

Agent 有随机性——同一任务跑两次可能走完全不同的路径。手工试几个 case 说明不了问题。评测干的事：**拿一批真实任务喂给它，用自动化测试判过没过**，让「好不好用」变成能量化、能复盘的结果。

**双维度**（D4）：
- **编码能力**：主基准 **SWE-bench-Live**（微软维护，每月收录 GitHub 最新真实 issue，未进训练数据）——让 Agent 自己定位自己修，Docker 里跑原项目测试判分。
- **工具调用能力**：辅助 **BFCL / τ-Bench**——测 Function Calling 正确性与 agentic 工具编排（初版落地形态见 T29）。

**迭代闭环**（用户驱动场景）：构造评测任务集 → 每次改 prompt/超参数/harness 方案 → 跑一遍评测 → 对比总体性能/成本指标与 fail2pass/pass2pass 任务级数据 → 发现问题 → 定位/观察 trace/排查/复现 → 修 → 同条件复测。

**不在本模块范围**：
- 数据采集与 trace 模型 → `07`（本模块**编排**与**报表**，数据层完全复用 07 §3.8）
- 运行时可靠性机制（检查点/测试闭环/约束校验）→ `12` Harness
- 任务集的构建工具（SWE-bench-Live 官方数据集拉取是脚本活，本模块定义流程与判分接口）

## 2. 与相邻模块关系

```
   SWE-bench-Live 数据集（HuggingFace）
        │ 拉取 + 封历史 + gold 校验
        ▼
   11 评测 driver（CLI：kdagent eval）
        │ 对每题调用 10 隔离执行
        ▼
   10 SubAgent（worktree + run_to_completion + 子 Agent 隔离上下文）
        │ 产出 model_patch + 完整 trace
        ▼
   SWE-bench 官方 harness（Docker）──► resolved / FAIL_TO_PASS / PASS_TO_PASS
        │ 回填 eval.run_id / task_id / passed / score
        ▼
   07 query 层：metrics_by_run / diff_runs / trace_by_task
        │
        ▼
   11 报表 + 失败归类（LLM 初判 + 人工复核）
        │
        ▼   一次一变量复测 → diff_runs 对比 → 12 Harness 迭代闭环
```

- **消费 `07`**：`run_id = config_hash`（prompt+超参+harness 配置哈希）；跑批时给每个 trace 打 `eval.run_id`/`eval.task_id`，判分回填 `eval.passed`/`eval.score`；对比走 `metrics_by_run`/`diff_runs`/`trace_by_task`（07 §3.8 数据层，本模块不重造）。
- **消费 `10`**：每题 = 一个隔离执行单元——`worktree` 隔离文件系统 + `run_to_completion` 非交互执行 + 子 Agent 隔离上下文（与 `isolation: worktree` 自动绑定）。
- **为 `12`**：评测是 Harness 迭代闭环的「度量仪」——一次一变量复测的结果驱动下一轮 Harness 改进。
- **与 `05` 无关**：跑批是长任务后台执行，不走 TUI slash command；入口是独立 CLI 子命令。

## 3. 详细设计

### 3.1 评测数据模型

```python
# eval/model.py
@dataclass
class EvalTask:
    instance_id: str            # 题号（SWE-bench-Live instance_id）
    repo: str
    base_commit: str            # bug 对应版本
    problem_statement: str      # 只给「要解决什么问题」，不给「怎么解决」
    fail_to_pass: list[str]     # 判分标准：原失败测试必须全过
    pass_to_pass: list[str]     # 原通过测试不能被碰坏
    gold_patch: str             # 官方参考补丁（gold 校验用）
    env_valid: bool = False     # gold 校验通过才 True

@dataclass
class EvalRun:
    run_id: str                 # config_hash：prompt + 超参 + harness 配置哈希
    config_snapshot: dict       # 哈希对应的配置明细（复现用）
    tasks: list[EvalTask]
    started_at: int
    # 判分后：每任务 resolved + fail_to_pass/pass_to_pass 明细

@dataclass
class EvalReport:
    run_id: str
    resolved: list[str]          # 通过题
    failed: list[FailureCase]    # 失败题 + 归类
    metrics: RunMetrics          # 通过率 / 成本 / 延迟 / token（07 聚合）
```

### 3.2 评测流水线（SWE-bench-Live 落地，T10）

```
准备阶段：
1. 拉任务：HF 加载 SWE-bench-Live（国内 HF_ENDPOINT 镜像），按 created_at 倒序挑最新 N 道
   （外部服务题跳过）；存 instance_id/repo/base_commit/problem_statement/FAIL_TO_PASS
2. 封 git 历史（防作弊，最关键的防抄）：git archive <base_commit> 抽文件树 → 新目录 git init
   重提一个 commit —— 副本只有单提交，Agent 翻 git log 也找不到正确答案
3. gold 校验环境：官方 gold 补丁先跑一遍，resolved=false 的题 = 环境失效，剔除
   （不剔除会把环境问题误算成 Agent 能力不足）

跑批阶段：
4. 对每题：在封史副本里跑隔离执行（10）→ 收 model_patch
   —— git add -A + git diff 导出，但排除运行时目录（.kdagent/.claude/）与所有测试文件
      （判分时 harness 注入自己的测试，补丁碰测试文件会冲突）
   —— 任务描述写进文件再喂（issue 的引号/美元符号会被 shell 吃掉）
5. 判分：SWE-bench 官方 harness（Docker）打 patch 跑测试，得 resolved 与 FAIL_TO_PASS/PASS_TO_PASS 明细

汇总阶段：
6. 回填 + 报表：07 聚合 metrics_by_run；failure 归类（§3.4）
```

**单题判定标准**：`FAIL_TO_PASS` 全过 **且** `PASS_TO_PASS` 无损坏 → resolved。只满足一半就是「修对但碰坏」或「没修对」。

**正常参照**：5-10 道最新题解 1-3 道属正常——题难（未进训练数据）+ 通过率上限由模型决定。要警惕的两种异常：gold 校验都不过（环境的锅）+ 补丁为空（Agent 中途退出）。

### 3.3 判分环境（Windows 平台）

SWE-bench 官方 harness 依赖 **Docker + Linux**（每道题对应 1-2G 预构建镜像；首轮拉镜像十来分钟，缓存后一分钟）。本项目开发机是 Windows：

- **方案 A（推荐初版）**：**WSL2 本地 Docker**——Windows 上跑 harness，开发机可行，镜像/数据国内配好加速。
- 方案 B（可选增强）：远程 Linux 机器跑判分，driver 通过 SSH/API 提交补丁。

### 3.4 失败归类（值钱的是「为啥挂」）

通过率只告诉你挂了。每道失败题翻 **07 trace**（Agent 每句话、每次工具调用、参数、报错、每轮 token、压缩点全在 trace），用一句话记失败原因，归入五类：

| # | 失败类型 | 特征（trace 里怎么看） | 对策方向 |
|---|---|---|---|
| 1 | 没定位到该改的文件 | 改错地方，patch 与目标无关 | 更强的检索/探索（10 Explore） |
| 2 | 定位对但修法不对 | patch 打了目标文件，测试仍不过 | 更强的模型/提示词 |
| 3 | 修对但碰坏别的测试 | FAIL_TO_PASS 过、PASS_TO_PASS 挂 | 回归防护（12 测试闭环） |
| 4 | 改动越滚越大 / 超时 / 工具报错 | patch 膨胀、中途放弃、工具被挡 | 框架毛病：修工具参数面/超时 |
| 5 | 约束冲突主动放弃 | 任务约束与代码现状冲突（如「不要改测试」+ 测试锁死 bug 行为） | 改约束措辞，别让 Agent 见测试就缩手 |

**归类方式**：LLM 读 trace 初判 + 人工复核（T30）。**信息保留测试**是另一种测法（对话开头告知多条信息，压缩后问还记得几条）——可作 01 压缩质量的辅助评测。

**复核界面**（T30 增量：可视化 + 交互）——Textual 内嵌「评测报告」屏幕（延续 D17 方案 A 风格：本地轻量、零外部依赖），三类交互支撑「定位 / 阅读 / 批注」：

| 交互 | 能力 | 实现要点 |
|---|---|---|
| **定位** | 失败题 → 展开 trace span 树 → 跳转具体事件 | 复用 07 trace 数据；span 树渲染 + 按「报错工具调用 / 压缩点 / 权限拒绝」过滤跳转 |
| **阅读** | 原始事件流可读渲染 | 流式碎片按轮拼回完整句子；工具调用参数/返回/报错逐事件挑出——**不让人肉翻 jsonl** |
| **批注** | 人工修正归类 + 写备注 | 写回 `{kdagent_dir}/eval/<run_id>/annotations.json`，复测可携带（同 run 再跑不丢批注） |

- **入口**：`kdagent eval --report <run_id>`；TUI `/eval report`（05 补注册，local 类型）。
- 与 07 `/metrics` 面板同风格、同一 Textual App 内（复用 05 挂载点），保持「本地轻量」一条线。

### 3.5 迭代闭环：一次一变量复测

```
复测铁律：一次只动一个变量 —— 还是那道题、那个模型、那份封史副本，
只换你改的那一处，重跑。
改了提示词又换模型，变好了也说不清是谁的作用。
```

**看什么**：不是盯着通过率涨没涨（通过率上限由模型定），而是**记录里那个具体现象还在不在**——原报错还报不报、被放弃的能力回来没有、要 30 轮的地方现在几轮收工。**现象消失 = 这次改对了**，哪怕分数纹丝不动（你修的是框架层的毛病，它决定「模型能力有没有被浪费」，不决定「模型能不能想出答案」）。

**对比工具**：`diff_runs(run_a, run_b)` → fail2pass（修复）/ pass2fail（回归）→ 命中 pass2fail → `trace_by_task` 取该 run 的 trace → span 树定位到具体 LLM 决策/工具调用/压缩点 → 复现（07 §3.8）。

### 3.6 对照测试：钉死模型（D4）

判断 Agent 好不好，至少拆三件事：**质量**（通过率，但必须钉死模型再比，不然比的是模型）、**效率**（同模型下 token/耗时/轮次——上下文管理做得好的框架每轮更精简）、**框架毛病**（工具报错/参数校验挡路/超时，只有翻记录看得见，是唯一能直接改的部分）。

**对照对象**：Claude Code 接同一个第三方模型（环境变量指向本项目配的模型）跑同一批题；对照条件全部钉死——同模型、同任务描述、同 base commit、同封史副本。**封历史在对照场景更要紧**：不封的话「谁更会翻 git log」会被误当成「谁能力更强」。

### 3.7 隔离跑批（复用 10）

每题在一个独立 `worktree` 中执行（文件系统隔离），子 Agent 用 `run_to_completion` 非交互跑。收益：题目间互不干扰、可并行、崩溃不影响主工作区。**复用 10 的 `isolation: worktree` + autoCleanup**：无改动即删、有改动保留供复查。

### 3.8 与 07 的接口契约

| 07 提供（数据层） | 11 使用（编排/报表） |
|---|---|
| `run_id = config_hash` 生成 | 每次跑批带 run_id，trace 打 `eval.run_id`/`eval.task_id` |
| 判分回填 `eval.passed`/`eval.score` | 判分后回填到 trace attributes |
| `metrics_by_run(run_id)` | 单版本：通过率/成本/延迟/token |
| `diff_runs(a, b)` | 跨版本：fail2pass/pass2pass/fail2fail/pass2pass |
| `trace_by_task(run_id, task_id)` | 失败定位入口 → span 树排查 |

**07 只保证数据层**；任务集管理、跑批编排、打分、报表、失败归类全在本模块（D17 边界：监控是 07+/metrics 面板，评测对比视图是 11）。

## 5. 验收标准

- [ ] `kdagent eval` 跑通 1 道题：封史副本 → 隔离执行 → 判分 → 回填，全程有 trace
- [ ] 封 git 历史生效：封史副本中 `git log` 只有一个 commit，Agent 翻不到答案
- [ ] gold 校验：环境失效题被剔除，不进入计分
- [ ] 单题判定正确：FAIL_TO_PASS 全过 + PASS_TO_PASS 无损坏才算 resolved
- [ ] 判分在 WSL2 Docker 跑通（国内镜像加速配置完毕）
- [ ] 跑批的 trace 携带 `eval.run_id`/`eval.task_id`；判分后回填 `passed`/`score`
- [ ] `metrics_by_run` 出单版本报表（通过率/成本/延迟/token）；`diff_runs` 出 fail2pass/pass2pass
- [ ] 失败题自动归类到五类之一（LLM 初判），人工可复核修正
- [ ] 复核界面：失败题可定位到 trace span、可读原始事件流（碎片拼回完整句）、可批注归类并持久化 `annotations.json`；`/eval report` 命令可用
- [ ] 失败定位闭环：pass2fail 命中 → `trace_by_task` → span 树定位到具体工具调用/压缩点
- [ ] 一次一变量复测：同条件重跑，diff_runs 对比出变化；具体现象消失判定为改对
- [ ] 对照测试脚本可用（Claude Code 接同模型、同批题、封史副本）
- [ ] 隔离跑批：多题并行不互相污染，worktree 无改动自动清理
