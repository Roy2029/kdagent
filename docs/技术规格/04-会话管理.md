# Coding Agent 技术规格 · 04 会话管理

> 状态：**已确认 v0.2**（2026-08-11）｜里程碑：阶段 2（能跑档）｜依赖：`02`（消息模型/写路径）、`01`（token 估算/压缩/落盘目录）｜被依赖：`05` 交互与 TUI（会话列表/恢复入口）、`08` 记忆（阶段 4 消费会话记录）

---

## 1. 目标与范围

**本模块让对话可以「存档读档」**。它回答：会话怎么落盘、怎么恢复、怎么管理生命周期。

- **JSONL 持久化**：每条消息一行，O(1) 追加、崩溃安全、增量恢复。
- **协议无关的内部表示**：落盘只存各厂商都有的东西（调用 ID/工具名/参数/输出），换 provider 历史不失效。
- **恢复四步**：逐行解析 → 链修复（时机在出口）→ token 检查 → 时间跨度提示。
- **生命周期**：创建/恢复/列表/删除 + 过期清理。

**不在本模块范围**：
- 消息的构造规矩与写路径规范 → `02` ConversationManager（本模块只做持久化视图）
- 上下文压缩机制 → `01`（恢复时超限调用它）
- 跨会话的**自动记忆/记忆治理**（user/feedback/project/reference）→ `08` 记忆系统（阶段 4）；本模块只做"原始会话记录"，不提取语义
- 项目指令文件（CLAUDE.md）加载 → `01` assemble_payload 已覆盖

## 2. 与相邻模块关系

```
        02 Agent（引擎）
           │ 写路径：conversation.add_*（02）→ 内存 history（01）
           ▼
     04 Session（聚合 conversation + 文件句柄）
           │ 每次消息写入后落盘 JSONL
           ▼
   {kdagent_dir}/sessions/{sid}.jsonl
   {kdagent_dir}/sessions/{sid}/tool-results/   ← 01 L1/L2 落盘目录（D7）
```

- **聚合 `02`**：`Session` 持有 `ConversationManager`，对引擎暴露同名语义化方法，内部"先写文件、再更新内存"（崩溃时从文件重建，不丢消息）。
- **引用 `01`**：恢复时 `history.estimate_tokens(None)` 全量估算；超 `AUTO_COMPACT_TRIGGER` 触发压缩；时间跨度提示用 `system_reminder` 注入。
- **为 `05` 提供**：`session list / resume / delete / clear` 的入口数据。
- **为 `08` 提供**：`tool-results/` 与 JSONL 是记忆提取与治理（阶段 4）扫描的对象。

## 3. 详细设计

### 3.1 为什么是 JSONL（选型）

| 方案 | 问题 |
|---|---|
| SQLite | 引入依赖、分发变复杂；会话场景用不上关系查询——杀鸡用牛刀 |
| 普通 JSON（整数组） | 追加需重读全文件（O(n)）；写一半崩溃 → 整个文件变非法 JSON，会话全毁 |
| **JSONL** | O(1) 追加、崩溃只影响最后一行（跳过即可）、逐行增量加载 |

天然适配 Agent 流式工作模式：每产生一条消息写一行，实时持久化。

### 3.2 存储格式：协议无关的内部表示

**关键原则**：不落盘任何厂商的原始线格式。Anthropic 用 `tool_use/tool_result` block、OpenAI 用 `tool_calls + role:tool`，直接存某家 JSON 会让会话跟厂商绑死，换模型历史立刻读不回来。落盘的是**内部表示**，恢复时由 `02` 的 adapter 翻译成当前厂商的线格式——换 provider 是配置层面的事。

```python
# sessions/records.py
from dataclasses import dataclass, field

@dataclass
class ToolUseRecord:
    tool_use_id: str
    tool_name: str
    arguments: dict

@dataclass
class ToolResultRecord:
    tool_use_id: str          # 指回 ToolUseRecord
    content: str
    is_error: bool = False

@dataclass
class ThinkingRecord:         # Anthropic Extended Thinking（D12：含）
    content: str
    signature: str | None     # 原样回传需要

@dataclass
class StepRecord:             # todo 步骤（T36：判据可选）
    description: str
    accept_criteria: str | None = None     # 完成型必写 / 探索型可省

@dataclass
class TodoItemRecord:         # todo 条目（03 TodoWrite 写入，12 检查点触发源）
    content: str
    status: str               # pending / in_progress / completed
    active_form: str = ""
    steps: list[StepRecord] | None = None

@dataclass
class SessionRecord:
    role: Literal["user", "assistant"]
    content: str = ""
    tool_uses: list[ToolUseRecord] | None = None
    tool_results: list[ToolResultRecord] | None = None
    thinking: ThinkingRecord | None = None     # 空字段整体省略
    todos: list[TodoItemRecord] | None = None  # 当前 todo 列表（会话级状态，见下）
    ts: int = 0                                # Unix 秒（整数，紧凑）
```

**一行示例**（两条消息，第三条是工具结果——**工具结果不是独立角色**，以 user 身份挂 `tool_results`，content 通常为空）：

```jsonl
{"role":"user","content":"帮我写一个 HTTP handler","ts":1736951405}
{"role":"assistant","content":"好的，让我看看...","thinking":{"content":"先读项目结构","signature":"sig_xxx"},"tool_uses":[{"tool_use_id":"t1","tool_name":"ReadFile","arguments":{"path":"/proj/main.py"}}],"ts":1736951407}
{"role":"user","tool_results":[{"tool_use_id":"t1","content":"from flask import Flask...","is_error":false}],"ts":1736951408}
```

**与 `02` Message 的映射**：
- `assistant.content` + `tool_uses[]` → TextBlock + ToolUseBlock
- `user.tool_results[]` → ToolResultBlock（`tool_use_id` 配对唯一线索）
- `assistant.thinking` → ThinkingBlock（T13 决定是否含）

**`todos` 字段（会话级状态，非消息）**：`03` TodoWrite 调用 → `execute()` 解析归一化（`[{content, status, activeForm, steps}]`，03 §3.6）→ 写入当前会话的 `todos` 随落盘。它**不参与 payload 的 messages 组装**——todo 快照进上下文走 `03` tool_result 回传 + `12` 检查点 system-reminder（4 时点刷新，`12` §3.2）；`04` 只负责持久化，供 `12` 系统侧刷新时点④（会话恢复）重灌快照。

**落盘的最终形态**：`02` 写路径在 append 前已过 `01.on_tool_result`（L1/L2 处理），故 JSONL 里存的是**历史中的最终形态**（大结果落盘后的预览文本），与内存 history 完全一致——恢复无需重放压缩，`tool-results/` 原文文件由 `01` 管理。

### 3.3 目录结构与命名

```
{kdagent_dir}/sessions/                          # D7，默认 .kdagent/
  20260811-143000-a3f7.jsonl                     # 会话历史
  20260811-143000-a3f7/tool-results/toolu_1.txt  # 01 L1/L2 落盘（同 id 目录，可与 .jsonl 并存）
```

- **会话 ID**：`YYYYMMDD-HHMMSS-xxxx`——前 15 位时间戳一眼看出创建时间，末尾 4 位十六进制随机后缀防同秒冲突（CI 场景多进程不撞文件）。
- **列表信息来自文件名 + JSONL 扫描**：创建时间从文件名读；最后活跃时间读最后一行 `ts`。文件通常不大，逐行扫描足够，不额外维护元信息文件。

### 3.4 会话管理器与恢复

```python
# sessions/manager.py
class SessionManager:
    def __init__(self, sessions_dir: Path): ...
    def create(self) -> Session: ...                          # 生成 id + 建 .jsonl
    def resume(self, sid: str) -> Session: ...                # 恢复（见下）
    def list(self) -> list[SessionMeta]: ...                  # 按最后活跃倒序
    def delete(self, sid: str) -> None: ...                   # 删 .jsonl + 同名目录
    def cleanup_expired(self, days: int = 30) -> None: ...    # 启动时调用
    def current(self) -> Session | None: ...

class Session:
    id: str
    file: Path
    conversation: ConversationManager          # 聚合 02 写路径

    def append_user(self, text, extra=None): ...    # 内部：conversation.add_user_message
    def append_assistant(self, blocks): ...         #      + 落盘（见 3.5）
    def append_tool_results(self, results): ...
```

**恢复四步**（`resume`）：

```
① 逐行解析 JSONL
    坏行跳过（崩溃截断的半行），不放弃整个会话
② 链修复 —— 时机在出口，不在此处
    恢复只加载原始记录 → 映射为 02 Message
    链修复交给 02 ConversationManager.repair_chain()，
    在每次发请求前（assemble_payload 之前）执行
③ token 检查
    usage = history.estimate_tokens(None)     # 无 last_usage → 全量估算
    if usage >= AUTO_COMPACT_TRIGGER: compactor.compact(history)   # 01
④ 时间跨度提示
    if now - last_ts > 24h:
        history.append(system_reminder("上次活跃于 {时间}，期间代码可能已变更，建议重读相关文件"))
```

**为什么链修复放在出口（发请求前）而不是恢复时**：悬空 tool_use 的来路很多（运行中用户中断、进程被杀、恢复时本身悬空），全部汇到"发请求那一刻"这一个出口——守在出口只写一遍修复，守在入口则要在每个产生不配对的地方各写一遍还容易漏。修复动作：

| 情况 | 处理 |
|---|---|
| `tool_use` 无配对 `tool_result` | 补一条 `is_error=True` 的 result：**"执行被中断，产生的影响需自行确认"**（措辞不能太满——工具可能没启动，也可能改了一半） |
| `tool_result` 无配对 `tool_use` | 直接剔除（留着只让 API 拒收） |
| **补位不写回文件** | 文件如实记录发生过什么；补位只是让这一次请求合法 |

### 3.5 写路径：先写文件、再更新内存

```
append_tool_results(results):
    # ① 02 写路径：过 01.on_tool_result → 组装 block → append 内存 history
    conversation.add_tool_results(results)
    # ② 落盘最新一条消息到 JSONL
    record = SessionRecord.from_message(last_message)
    file.write(json.dumps(record) + "\n")
```

**顺序保证**：先写文件再更新内存计数——若写文件成功但更新内存前崩溃，下次恢复从文件重建，消息不丢；反向则"内存有、文件无"，消息永久丢失。所有写路径（append_user / append_assistant / append_tool_results）遵循同一顺序。

### 3.6 过期清理

- 启动时扫描 `sessions/`，删除超过 `CLEANUP_EXPIRED_DAYS`（默认 30）天无活跃的会话（`.jsonl` 的 mtime 或最后一行 `ts` 判定）。
- **可配置、可开关**（D12）：天数与是否启用由配置文件控制（如 `cleanup_expired: {enabled: true, days: 30}`）；关闭则不自动清理，交由用户手动管理。
- 列表按最后活跃时间倒序，最近用过的排最前。

## 5. 验收标准

- [ ] 每条消息写入 JSONL 为一行，流式实时落盘（不攒批）
- [ ] 模拟崩溃截断最后一行 → 恢复时跳过坏行，前序消息完好
- [ ] 恢复会话 → 消息映射为 `02` Message，发请求不被 API 拒收（交替/配对合法）
- [ ] 悬空 `tool_use` → 发请求前补"执行被中断"错误结果；**不写回文件**
- [ ] 孤儿 `tool_result` → 剔除
- [ ] 恢复超长会话（token 超阈）→ 触发 `01` 压缩
- [ ] >24h 恢复 → 插入时间跨度提示
- [ ] `list()` 按最后活跃倒序；启动时 30 天过期会话被清理
- [ ] 主 provider（DeepSeek / OpenAI 兼容）记会话、切 Anthropic 恢复 → 历史不失效（协议无关）
- [ ] `TodoWrite` 解析后写入 `SessionRecord.todos` 随会话落盘；恢复时 `12` 时点④重灌快照，`05` 面板从状态读渲染
- [ ] thinking 块恢复后连同签名原样回传（Anthropic 路径；DeepSeek 无此字段，落盘为空）
