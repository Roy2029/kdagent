# Coding Agent 技术规格 · 08 记忆系统

> 状态：**已确认 v0.2**（2026-08-13，T1-T4 已决）｜里程碑：阶段 4（好用档：静默记忆）+ 生产级（主动/Dreaming）｜依赖：`02`（Agent.run 结束提取时机）、`01`（加载管线/前缀缓存/压缩联动）、`04`（会话 JSONL 是提取源）｜被依赖：`05`（/memory 命令）、`07`（生产级记忆信号源）、`12`（Harness 评估记忆效果）

---

## 1. 目标与范围

**本模块回答：Agent 怎么「跨会话记住」？**

- **静默线**：用户零感知——自动提取值得长期复用的信息，新会话自动加载（好用档）。
- **主动线**：Agent 可主动管理记忆（生产级）。
- **治理（Dreaming）**：对已有记忆去重合并、冲突消解、修剪索引（生产级）。

**本模块的路线基调（T1-T4 待确认，见 §6）**：参考 Claude Code / MewCode 的**文件生态路线**——记忆是普通 Markdown 文件，人类可读可编辑、git 可追踪；**不做向量检索**，检索交给 LLM 与文件工具；**注入式静默读**（MEMORY.md 索引注入）+ **单阶段 fork 治理**。

**不在本模块范围**：
- 向量数据库 / embedding 基建（T2 排除，见 §6）
- 会话内容持久化 → `04`（JSONL 是记忆提取的**源**，本模块不重存）
- 记忆效果的量化评估 → `12` Harness（本模块提供提取/治理数据点）
- MCP / Skill 生态 → `09`

## 2. 与相邻模块关系

```
   02 Agent Loop ──run 结束──► 提取（节流门槛后单次调用）──► {kdagent_dir}/memory/*.md
        │                        （主上下文前缀缓存 + 追加提取指令 → 增/改/删 + 更新索引）
        │
        │ 新会话启动
        ▼
   01 assemble_payload ──► 加载 CLAUDE.md + MEMORY.md 索引（同一管线）──► messages
        │
        └── 压缩 ──► 每轮末已提取，压缩时无需专门 Flush（§3.7）
   04 会话 JSONL ──► 提取代理的输入源
   07 trace ──► （生产级）会话回放/记忆信号源
   05 /memory 命令 ──► 查看/管理记忆（本模块定义，05 补注册）
```

- **消费 `02`**：提取挂在 Agent Loop 每轮末（最终回复、无工具调用的收尾轮）；主动线提示词注入 system。
- **消费 `01`**：记忆索引与 CLAUDE.md 走同一加载管线注入 messages（不新增机制）。
- **消费 `04`**：提取代理用会话 JSONL 作为「最近发生了什么」的输入源。
- **为 `05`**：定义 `/memory` 命令需求（概要/list/add/clear），05 补注册。
- **为 `12`**：记忆命中率、提取准确率是 Harness 评估数据点。

## 3. 详细设计

### 3.1 总体架构：三条线 + 一个闭环

```
   ┌─────────── 静默读（注入式）───────────┐
   │   新会话 → 注入 MEMORY.md 索引        │
   ▼                                      │
 用户会话 ──每轮末──► 静默写（节流触发轻量提取）──► memory/*.md ──► MEMORY.md 索引
   ▲                                      │
   │            ┌─────────────────────────┤
   │            ▼                         │
 主动读/写 ◄── 通用文件工具 + 提示词引导 ◄─┘
   │
   └── Dreaming（单阶段 fork 治理，≥24h）──► 合并/删除/修正/修剪索引
```

**关键交接点**：
1. **文件是唯一真相来源**：提取写入、主动读写、治理整理都围绕 `memory/*.md` 这一层。
2. **MEMORY.md 是汇合点**：治理修剪它，静默读注入它。
3. **每轮末提取保证压缩不丢记忆**：压缩丢弃上下文前，值得记的已落盘。

### 3.2 数据模型：四类记忆 + 文件结构

**四类分类**（决定落盘目录）：

| 类别 | 含义 | 目录 |
|---|---|---|
| `user` | 用户偏好/风格（跨项目成立） | 用户级 `~/.kdagent/memory/` |
| `feedback` | 纠正反馈（"不对，应该…"） | 用户级 `~/.kdagent/memory/` |
| `project` | 项目知识（换项目不适用） | 项目级 `{work_dir}/.kdagent/memory/` |
| `reference` | 外部链接/资料 | 项目级 `{work_dir}/.kdagent/memory/` |

```
{kdagent_dir}/memory/
  MEMORY.md            # 索引文件（注入上下文；上限 200 行 / 25KB）
  user-prefers-any.md  # 每条记忆一个独立文件（增删改不干扰，删=删文件）
  feedback-lock-var.md
  project-deadline.md
```

**记忆文件**（frontmatter 是检索/治理的元信息，正文是事实）：

```yaml
---
name: user-prefers-any
description: 用户偏好使用 any 而非 interface{}
type: feedback
---

用户明确要求使用 any 替代 interface{}。
**Why:** 现代类型语法更简洁
**How to apply:** 所有新写的泛型代码用 any
```

**MEMORY.md 索引**（只存指针，每行一条）：

```markdown
- [偏好 any 语法](user-prefers-any.md) — 用户要求用 any 替代 interface{}
- [项目用 golang-migrate](project-migration-tool.md) — 数据库迁移工具选型
```

- **为什么目录而非单文件**：每条记忆独立增删改；**为什么独立于 CLAUDE.md**：指令文件是手维护/进 git/团队共享，自动记忆是机器生成/个人专属，混在一起污染（放 `.kdagent/` 加 `.gitignore` 可选）。
- **索引上限 200 行/25KB** ≈ 2000-3000 tokens ≈ 200K 窗口的 1-2%——长期记忆固定开销压到零头，不挤工作记忆（mewcode 取值，沿用）。

### 3.3 静默读：注入式（T1 建议）

新会话启动 → `01` assemble_payload 加载 `CLAUDE.md` + `MEMORY.md` 索引，走**同一管线**注入 messages（遵循 `01` 的 append-only 规矩，不新增机制）。用户无感，Agent 自动「想起来」。

> 说明：注入的是**索引指针**而非全文；模型判断某条记忆与当前任务相关时，用 `ReadFile` 读对应 `.md` 文件取详情（主动线，§3.5）。

### 3.4 静默写：双门槛节流 + 前缀缓存复用

> 设计约束：**不能是「每轮末 fork 完整子 Agent」的高频高成本设计**（贵 + 隐含对 `10` 的运行时依赖）。但也不能是「廉价档模型读增量片段」——**缓存按「模型 + 前缀」分，换模型缓存不命中反而贵**。正解 = 双门槛节流 + **复用主上下文前缀缓存**。

**触发 = 廉价检查**（每次 `Agent.run()` 结束——一次用户输入处理完、不再调工具；**非**每个 ReAct iteration，无 LLM 调用，两次比较）：

```
if 距上次提取 < EXTRACT_MIN_INTERVAL（10 分钟）: return        # 时间节流
if 距上次提取的累计增量 < EXTRACT_MIN_DELTA（20K tokens）: return # 量级节流
后台执行提取
```

**增量窗口是滑动窗口**：从「上次静默写点」累计到「现在」，**跨多次 run 累积**，而非当前这一次 run——短单次输入可能不触发，长会话多次输入累积会越过门槛。累计增量用 `01` 的 `estimate_tokens` 差值（上次提取点打 token 标记）。大多数 run 在第一道门就返回、**零 LLM 调用**。

**提取形态 = 主上下文前缀缓存 + 追加提取指令**：

- **输入** = 主代理当前完整 messages（`01` append-only，运行中已作为前缀缓存命中）+ 追加一条**记忆提取指令**
- **模型** = **与主对话相同**（缓存按模型分，换 cheap 模型缓存不命中、反而贵）
- **成本** = 主上下文按缓存命中 `C_hit`（≈`C_in/10`，DeepSeek 折扣大）+ 提取指令按 `C_in`（少量）
- **为什么优于「读增量重理解」**：模型在完整上下文末尾工作，无需重新理解碎片；边际成本主要是已缓存前缀的命中价
- **输出** = 结构化操作集 `[{action: create|update|delete, name, frontmatter, content, index_line}]`
- **本地执行** = create/update → 写 `memory/{name}.md` + 更新 MEMORY.md；delete → 删文件 + 移索引；**路径限 `memory/` 内**（复用 `06` 路径沙箱）
- 单次调用不够时最多追加 1-2 次小调用；`10` 落地后可升级为完整子代理形态

**提取指令**（追加为最后一条 user 消息；交给 LLM 判断，不写规则引擎）：

```
下面是当前的记忆目录清单和最近对话的结尾部分。
分析对话，提取值得长期记忆的信息。

操作：
- 创建新记忆文件（写 frontmatter + 正文，更新 MEMORY.md 索引）
- 更新已有记忆文件（如果信息有变化）
- 删除过时记忆文件（同时从 MEMORY.md 移除指针）

分类：user / feedback / project / reference
已有相同含义的记忆不要重复创建。
没有值得记忆的内容就什么都不做。
```

- **去重是天然的**：模型拿到全部现有记忆清单，「用 any 代替 interface{}」和「不要用 interface{}」能被识别为同一件事，无需自己实现相似度算法。
- **「没有值得记忆的内容就什么都不做」**：大多数轮次（「帮我加个函数」「好的」）没有长期价值，不创建 → 防垃圾淹没。
- **与主代理互斥**：主代理本回合已主动写过记忆时，提取跳过该区间，避免重复劳动。

### 3.5 主动线：通用文件工具 + 提示词引导（T2/T3 建议）

**不发明专用 `memory_search` / `memory_save` 工具**。Agent 的主动读/写走普通文件工具：

- **读**：模型用 `ReadFile` 读 `MEMORY.md` 索引 → 按指针 `ReadFile` 读主题文件详情；`Glob`/`Grep` 搜记忆目录。
- **写**：模型用 `Write`/`Edit` 遵循**两步保存法**——先写主题文件，再在 MEMORY.md 加一行索引。

**记忆使用说明注入 system prompt**（让模型知道"何时该翻记忆"）：

```
记忆是四类 Markdown 文件（user/feedback/project/reference），
MEMORY.md 是索引。回答涉及过往工作/决策/偏好/待办时，
先读 MEMORY.md 定位，再读对应文件取详情。
新增记忆：先写主题文件，再在 MEMORY.md 加一行指针。
```

**为什么通用工具**：工具面最小化，零专用基建；记忆文件对模型和人类都是普通文件（可直接编辑器查看/修改，git 追踪）；检索时机决策权完全交给模型。**代价**：检索质量依赖模型自觉——可接受（与 T2 注入式配套）。

### 3.6 Dreaming 治理：单阶段 fork 代理（T4 建议）

**定位**：只管写不管整理，记忆目录会变成垃圾场（三条"不要自动 push"、两条矛盾的项目截止日期、过期信息占满索引配额）。治理 = 定期后台整理。

**触发门控**（懒检查，挂在每轮 Loop 末；命令行工具无常驻 cron，只能在活跃时顺带检查）：

```
if 记忆目录不存在: return
if 距上次整理 < 24h: return          # 时间门（锁文件 mtime）
if 10 分钟内已扫描: return            # 扫描节流
if 累积会话数 < 5: return             # 会话门
if 获取锁失败: return                # 防并发
后台 fork 受限代理执行整理
```

**锁文件**（`memory/.consolidate-lock`，一个文件两个用途）：内容存 PID，mtime 在获取时刷新 ≈ 上次整理完成时间。锁判定：文件存在 + mtime < 1h + PID 存活 → 放弃；否则写 PID + 回读确认。失败用 `utimes` 回退 mtime（下次门控能过）；崩溃残留 PID 由"进程已死"回收；>1h 视为过期。

**整理四阶段**（LLM 驱动，非规则引擎）：

1. **定位**：ls 记忆目录、读 MEMORY.md、浏览现有记忆——先搞清现状
2. **收集信号**：grep 最近会话记录，找新信息/矛盾（不全量读，针对性搜）
3. **整理**：合并重复（三个"不要 push"→ 一个）、删被证伪、修矛盾、**相对日期转绝对**（"昨天"→ 具体日期）
4. **修剪索引**：更新 MEMORY.md，删失效指针、压长行、加重要新记忆，**维持在 200 行/25KB 内**

**与提取的关系**：提取管「写」（高频、单次小），治理管「整理」（低频、批量）——记账与月末对账。

### 3.7 与上下文压缩联动

`01` 压缩本质是摘要提炼、丢弃上下文。**本方案不需要压缩前专门 Flush**：静默提取每轮末执行，值得记的已随轮落盘；压缩发生时没有"未落盘的宝贵内容"。相比 OpenClaw「压缩前现场写一次」与 ClaudeCode「后台维护 summary.md 供压缩复用」，本方案以**提取频率**换取**无压缩钩子**——`01` 压缩链路零改动。

> 备注：ClaudeCode 的 SessionMemory（跨会话摘要）在阶段 5 若有压缩成本压力，可评估「压缩复用摘要」优化；好用档不引入。

### 3.8 与 04 / 07 的关系

- **04 会话 JSONL**：提取代理的输入源（"最近发生了什么"从会话读）；不重存。
- **07 trace**（生产级）：会话回放数据可作为记忆提取与治理的信号源（OpenClaw 的"召回追踪"变体）。好用档不依赖；`12` 评估时启用。

### 3.9 关键参数

| 参数 | 初值 | 含义 |
|---|---|---|
| MEMORY.md 上限 | 200 行 / 25KB | 注入上下文固定开销 ≤1-2% 窗口 |
| 提取检查点 | 每次 `Agent.run()` 结束 | 非每个 ReAct iteration |
| 提取触发门槛 | ≥10 分钟 + 距上次提取累计增量 ≥20K tokens | 滑动窗口（跨多次 run 累积） |
| 提取输入 | 主上下文（缓存命中）+ 追加提取指令 | 同主对话模型；边际成本 ≈ C_hit + 指令 C_in |
| 提取写入边界 | 路径限 memory/ 内 | 复用 `06` 路径沙箱 |
| Dreaming 门控 | ≥24h + 会话数≥5 + 锁 | 懒检查 |
| 锁过期 | 1h | 防 PID 复用永久阻塞 |
| 分类 | user/feedback/project/reference | frontmatter `type` 决定目录 |

## 5. 验收标准

- [ ] 新会话启动 → `MEMORY.md` 索引（用户级+项目级）随 CLAUDE.md 走同管线注入上下文
- [ ] 对话中纠正偏好（"应该用 X"）→ 提取触发创建记忆文件 + 更新索引；主代理无感、不阻塞
- [ ] 短对话（累计增量 <20K tokens）不触发提取；10 分钟内不重复触发；多数 run 零 LLM 调用
- [ ] 提取输入 = 主上下文（前缀缓存命中）+ 提取指令，用**同主对话模型**；写入路径限 `memory/` 内、不碰项目代码
- [ ] 重复信息不重复创建（LLM 去重）；无长期价值轮次不创建记忆
- [ ] 记忆文件 frontmatter（name/description/type）规范、正文人类可读、git 可追踪
- [ ] 主动线：模型读索引→读详情；两步保存法写入；`/memory` 命令可查看/管理
- [ ] Dreaming 门控通过后：合并重复/删过时/修矛盾/修剪索引；锁文件防双进程并发；失败回退 mtime
- [ ] 压缩时记忆不丢（每轮末已提取，`01` 链路零改动）
- [ ] 索引超 200 行/25KB 被治理修剪回限内

## 6. TO-DECIDE

> ✅ 已决（2026-08-12，T1/T2/T3）：记忆采用 **Claude Code / MewCode 文件生态路线**——**注入式静默读**（MEMORY.md 索引注入，200 行/25KB 上限）+ **无向量/side-query 检索**（检索 = 翻索引 + ReadFile 详情）+ **通用文件工具主动线**（无专用 memory_search/save，提示词引导）。自洽逻辑：注入式 → 检索退化 → 主动线无专用工具 → 无召回追踪信号 → 治理无需三阶段（T4 配套）。

| # | 待决项 | 建议（推荐） |
|---|---|---|
| T4 | **Dreaming**：三阶段睡眠模拟（OpenClaw）vs 单阶段 fork 代理整合（ClaudeCode/mewcode） | **单阶段**——门控+锁+四阶段整理，LLM 判断替代打分；三阶段依赖的召回追踪信号已被 T2/T3 排除 |

**T4 两方案关键设计对比**：

| 维度 | OpenClaw 三阶段睡眠模拟 | ClaudeCode/mewcode 单阶段整合 |
|---|---|---|
| 触发 | 托管 Cron 定时（默认每晚） | 懒检查门控（≥24h + 会话数≥5 + 锁） |
| 处理主体 | 启发式规则/打分流水线（非 LLM） | 一个 fork 的 LLM 代理 |
| 信号输入 | 结构化两路摄入（文件分块 + 会话增量行）+ 召回追踪计数 | LLM 自己读 transcript 判断 |
| 巩固逻辑 | 三阶段状态机：Light 打分筛选 → REM 跨候选找模式 → Deep 多维排名 Top-N promote | 单轮 LLM 自由发挥：合并 / 删 / 修 / 修剪索引 |
| "什么值得记住" | 六维打分（频率/相关性/多样性/近因性/跨天巩固/概念覆盖）+ 阈值 | LLM 语义判断 |
| 写入 MEMORY.md | 仅 Deep Dreaming 阶段 promote Top-N | 整理结束时写回 |
| 依赖的底层能力 | 专用检索工具（memory_search）的**召回追踪信号** | LLM 能力 |
| 工程复杂度 | 高（状态机 + 信号管线 + 打分器） | 低（一个受限代理 + 提示词） |
| 可解释性 | 可解释（"为什么记住"→ 频率/分数可答） | 不可解释（模型自由裁量） |

**本质区别**：三阶段 = **结构化信号处理**（治理拆成可判定的流水线，工程重但可控可解释）；单阶段 = **一次 LLM 判断**（治理交给模型自由发挥，工程轻但不可解释）。

**关键联系**：三阶段的强输入（召回追踪信号）依赖专用检索工具，**已被 T2/T3 排除**——选 ClaudeCode 路线则单阶段是唯一配套；若未来想升级 OpenClaw 式治理，需先回退 T2/T3 引入 `memory_search`。
