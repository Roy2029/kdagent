## 1. 目标与范围

**本模块是整套系统的横切基础设施**。它回答一个问题：Agent 在有限的上下文窗口内，如何"看得全、看得久、看得便宜"。

上下文窗口的生命周期贯穿 Agent 设计——消息格式、LLM 响应、工具调用、压缩、记忆都以「上下文」为时序线索。本模块定义这条线索的**机制**：

- **静态层**：系统提示词如何组装、如何放进正确的字段以保护前缀缓存
- **动态层**：上下文如何演进（append-only、动态指令注入）
- **压缩层**：三层压缩体系（大结果落盘 / 在线摘要 / Auto-Compact），让 Agent 在有限窗口内长时间工作
- **兜底层**：强制压缩线、紧急压缩、熔断，保证不瘫痪

**不在本模块范围**（由其他模块定义）：
- System Prompt 的**具体文案**（七模块内容）→ `02` 核心引擎
- 工具描述的**具体内容** → `03` 工具系统
- 记忆系统的**语义与提取策略** → `08` 记忆系统（本模块只定义压缩机制，记忆消费本模块的压缩产物）

## 2. 设计原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | **保护前缀缓存** | 历史的每条消息"写入即终态"，永不改写。前缀稳定 → Prompt Cache 命中率最大化。任何"每轮重新评估旧消息"的设计都是反模式 |
| P2 | **append-only，最小扰动** | 新信息只追加在历史尾部，绝不改写中部。动态指令用 system-reminder 注入 messages 而非改动 system 字段 |
| P3 | **能轻则轻** | 轻量手段（落盘、在线摘要）能扛住的场景，绝不动用昂贵的全量摘要（Auto-Compact）。三层按成本递增排列 |
| P4 | **token 估算锚定真实用量** | 用上次 API 返回的真实 token 数为基准，只对之后新增的增量做估算，把误差压缩在最后一小段，避免误差随对话累积 |

## 3. 静态层：Prompt 组装与缓存保护

### 3.1 三字段划分（缓存保护是第一理由）

每次 API 请求含三字段：`system`、`messages`、`tools`。稳定内容放 system（可缓存），动态内容放 messages（保护缓存），工具描述放 tools（API 规范）。

| 信息来源 | 字段 | 原因 |
|---|---|---|
| 静态 System Prompt（七模块） | system | 每轮生效、内容稳定，可缓存 |
| 环境上下文（工作目录/OS/Git 状态） | system | 会话内不变，可参与缓存分层 |
| 工具描述 | tools | API 规范要求 |
| 项目指令文件（CLAUDE.md） | messages（system-reminder） | 内容可能长，放 system 会稀释注意力且破坏缓存 |
| 自动记忆 | messages | 动态内容 |
| 动态上下文（MCP/Skill 列表等） | messages | 需在特定时机注入 |
| 对话历史 | messages | API 规范要求 |

**缓存分层**：环境上下文是"会话级稳定"，可独立管理（全局缓存 + 会话级缓存分层）。原则：**system 字段内任何字符变化都会使整段缓存失效**，所以 system 内容一旦确定，会话内绝不变更。

### 3.2 system 组装管线

```
function assemble_system_prompt(config) -> str:
    parts = [角色设定, 行为准则, 工具使用指南, 代码质量规范, 安全边界, 任务执行模式, 输出风格]
    if config.planMode: parts.append(PLAN_MODE_INSTRUCTIONS)
    return "\n\n".join(parts) + "\n\n" + build_environment_context(config)
```

- 七个模块的**具体文案**由 `02` 定义；本模块只约定组装结构与放置规则。
- 关键指令放**首尾**（Lost in the Middle），关键规则在 System Prompt 与工具描述中**双重强化**。
- 指令尽量**正面表述**（"默认不写注释"而非"不要写注释"）。

### 3.3 payload 组装

```
function assemble_payload(config, history) -> Payload:
    system = assemble_system_prompt(config)
    messages = []
    # 动态内容全部以 system-reminder 注入 messages，保护 system 缓存
    if instr = load_instruction_files(config.work_dir): messages.append(reminder(instr))
    if memories = load_memories(config):                messages.append(reminder(memories))
    if dyn = build_dynamic_context(config):            messages.append(reminder(dyn))
    messages.extend(history)                              # 动态内容放历史之前，利用近因效应
    tools = registry.get_enabled_tool_schemas()
    return Payload(system, messages, tools)
```

### 3.4 完整 payload 示例（含会话中途激活的 MCP/Skill）

以「用户请求修复 auth.py 空值 bug，会话进行中又连接了 github MCP」为例，展示三个字段全貌：

```
{

            "【行为准则】…\n【工具使用指南】…\n【代码质量规范】…\n"
            "【安全边界】…\n【任务执行模式】…\n【输出风格】…\n\n"
            "## 环境上下文\n工作目录：/home/you/proj\nOS: Windows 10…\nGit: main@a1b2c3d",

  "messages": [
    {"role":"user","content":[{"type":"text","text":
      "<system-reminder>\n## 项目指令（CLAUDE.md）\n…技术栈、编码约定…\n</system-reminder>"}]},
    {"role":"user","content":[{"type":"text","text":
      "<system-reminder>\n## 自动记忆\n…用户偏好、项目约束…\n</system-reminder>"}]},
    {"role":"user","content":[{"type":"text","text":
      "<system-reminder>\n## 可用 Skill\n- code-review：审查代码变更…\n- tdd：测试驱动开发…\n</system-reminder>"}]},
    {"role":"user","content":[{"type":"text","text":
      "<system-reminder>\n## 已连接 MCP Server\n- grafana：查询 Prometheus…\n</system-reminder>"}]},
    # ↑ 以上 system-reminder 与下方用户输入在序列化时合并为同一条 user 消息（满足交替规则）
    {"role":"user","content":[{"type":"text","text":"帮我修复 auth.py 里的空值引用 bug"}]},
    {"role":"assistant","content":[{"type":"text","text":"我先定位空值来源…"},
        {"type":"tool_use","id":"toolu_01","name":"Grep","input":{"pattern":"None|null","path":"auth.py"}}]},
    {"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_01","content":"…匹配结果…"}]},
    # …… 对话继续若干轮 ……
    # ── 会话中途：用户连接了 github MCP ──
    {"role":"user","content":[{"type":"text","text":
      "<system-reminder>\n## 已连接 MCP Server（新）\n- github：仓库、PR、issue 管理…\n"
      "新工具以 mcp_github_* 前缀提供。\n</system-reminder>"}]},
    {"role":"assistant","content":[{"type":"text","text":"我查一下这个函数的仓库历史…"},
        {"type":"tool_use","id":"toolu_02","name":"mcp_github_search_repo","input":{"q":"auth"}}]},
    {"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_02","content":"…"}]}
  ],

  "tools": [
    {"name":"ReadFile","description":"…"},
    {"name":"Grep","description":"…"},
    {"name":"mcp_grafana_query","description":"…"},        # 会话开始时已连接
    {"name":"mcp_github_search_repo","description":"…"}     # 中途激活 → 下一轮起出现在 tools
  ]
}
```

**要点**：
1. **MCP/Skill 的上下线、新增**确实都通过 `<system-reminder>` 注入 messages，**不改动 system 字段** → 前缀缓存不受影响。
2. 中途激活的 MCP，其工具会在**下一轮 payload 的 tools 字段**出现（工具延迟加载，见 `09` 工具生态）；同时一条新的 system-reminder 通知模型 server 与 `mcp_github_*` 前缀。
3. 注意 tools 字段中途增项会使该断点起的缓存命中局部失效——这正是"工具延迟加载"（只加载用到的、避免频繁增删）存在的原因。
4. 所有 user 块（reminder + 用户输入 + tool_result）在序列化时合并/规范化为合法的 user/assistant 交替序列。

## 4. 动态层：append-only 与 system-reminder

### 4.1 写入即终态

- 每条消息（含工具结果）在写入历史的那一刻就是**最终形态**，后续任何轮次不再改动——这是 P1 的直接实现。
- 推论：所有对工具结果的预处理（落盘、摘要）必须发生在**写入历史之前**。

### 4.2 system-reminder 注入机制

实现为一个带 XML 标签的 user 消息：

```python
def system_reminder(content: str) -> dict:
    return {"role": "user", "content": [{"type": "text",
            "text": f"<system-reminder>\n{content}\n</system-reminder>"}]}
```

- 典型场景：MCP Server 上下线、Skill 列表变更、子 Agent 类型声明、温和提醒（如"任务工具未使用，复杂任务可考虑用 Task"）、项目指令注入。
- **安全约束**：system-reminder 内容若来自外部（MCP 返回、网络内容），需警惕 **prompt 注入**——外部文本可能伪装成指令。外部内容要包裹/标注来源。
- 多个 user 块（reminder + 用户输入）在序列化层自动合并为一条 user 消息，满足 user/assistant 交替规则，压缩模块无需操心交替。

## 5. 压缩层：三层压缩体系

### 5.1 总览

| 层 | 手段 | 信息损失 | API 开销 | 作用域 | 触发 |
|---|---|---|---|---|---|
| **L1** | 大结果落盘 | 几乎为零 | 零 | 单条 >50K 字符 / 单轮聚合 >200K 字符 | 入口处 |
| **L2** | 工具结果在线摘要 | 中低 | 一次 LLM 调用 | 中等结果 + 低信息密度 + 经济性判定通过 | 入口处 |
| **L3** | Auto-Compact（全量摘要） | 中 | 一次 LLM 调用 | 累积 token 逼近窗口上限 | 每轮 API 前 |

- **L1 管入口、L3 管累积**：L1 挡住单次超大输出；L3 兜底几十轮累积。
- **L2 是用户原创增量**（MewCode 参考实现没有此层）：处理"比落盘阈值低、但仍有噪声"的中等结果，在入口处现场压缩，降低上下文噪声、延长窗口寿命、减少 L3 触发频率。代价是更频繁调用 LLM（但利用前缀缓存 + 减少后续每轮携带的体积，通常回本）。
- 三层协作的核心：**进入历史的消息都是 L1/L2 处理过的最终形态**，L3 估算 token 时拿到的是真实大小。

### 5.2 L1：大结果落盘

**单条超限**：工具结果 > `TOOL_RESULT_SAVE_THRESHOLD`（50,000 字符 ≈ 12.5K token）时，完整内容写盘，历史中只放预览 + 文件路径：

```
<persisted-output>
输出太大（80KB），完整内容已保存到：
{kdagent_dir}/sessions/{session_id}/tool-results/toolu_abc123.txt

预览（前 2KB）：
=== 测试运行结果 ===
PASS: TestUserCreate (0.02s)
...
</persisted-output>
```

**单轮聚合超限**：一轮并行调用的所有结果合并为一条 user 消息，写入前合计总量，超 `TOOL_RESULT_AGGREGATE_THRESHOLD`（200,000 字符）时，从最大的结果开始落盘替换成预览，直到总量降到预算以内。

**读回闭环**：ReadFile 读回落盘文件时，结果**不做二次落盘**（否则永远读不到全文）；用 offset/limit 参数按需读段。

### 5.3 L2：工具结果在线摘要压缩（原创）

> 设计依据：[工具结果实时压缩设计.md](../子模块设计讨论与资料/工具结果实时压缩设计.md)

**问题**：L1 只处理超大的结果（>50K 字符），但中等结果（如 8K–12.5K token 的错误堆栈、网页结构）也会在长上下文里成为噪声，且每次轮询都携带。Auto-Compact 又太贵、触发太晚。

**方案**：工具结果返回后、写入历史前，若判定值得，利用当前上下文前缀即刻执行一次"工具结果摘要"，以摘要 S 替换 X 写入历史。

**经济性模型**（用户建模，已校验）：

```
符号：P=已有上下文(token)  X=工具结果(token)  S=摘要(token)  I=压缩指令(token)
      C_in / C_out / C_hit = 无命中输入 / 输出 / 缓存命中输入 计价

压缩相对不压缩的总成本差：
  T1 - T0 = C_in*(I+S) + C_out*S + C_hit*P - C_hit*(X-S)*N

回本条件（压缩后还需复用 N 轮才划算）：
  N > (C_in*(I+S) + C_out*S + C_hit*P) / (C_hit*(X-S))
```

**关键因素**：
1. **压缩率 α = S/X**：越小越值得。与信息类型相关——错误堆栈/网页/日志压缩率高，代码/设计文档压缩率低。
2. **X/P 比值**：结果相对已有上下文越大越值得。
3. **(C_in+C_out)/C_hit**：模型相关的固定值，通常 50–80（DeepSeek 150/160），越小越值得。

**决策函数**：

```python
def should_online_compress(result, p_tokens: int, usage_stats) -> bool:
    X = estimate_tokens(result.content)
    # 1) 作用域门槛：太小不值得、太大走 L1 落盘
    if X < ONLINE_COMPRESS_MIN or X >= TOOL_RESULT_SAVE_THRESHOLD_TOKENS:
        return False
    # 2) 信息密度：高密度文本（代码/设计文档）不压缩，避免丢信息
    if info_density(result) == HIGH:
        return False
    # 3) 经济性判定：由类型先验估计压缩率 α，算回本复用次数
    alpha = EXPECTED_RATIO_BY_TYPE[result.type]        # 先验，待实测校准
    S = max(1, int(X * alpha))
    I = COMPRESS_INSTRUCTION_TOKENS
    break_even_N = (C_in*(I + S) + C_out*S + C_hit*p_tokens) / (C_hit*(X - S))
    expected_N = estimate_remaining_turns(p_tokens, usage_stats)
    return expected_N > break_even_N
```

**信息密度分类**（启发式，可按内容特征判定）：
- **LOW**（压缩率高）：错误堆栈、日志输出、网页结构、搜索结果列表、CI 输出
- **HIGH**（不压缩）：源代码、设计文档、配置文件、用户要求的原文、**todo 快照**（`12`：任务状态必须保真，L2 不得摘——检查点对表依赖最新快照）

**摘要 Prompt**（L2 用，区别于 L3 的 9 部分长摘要）：要求保留关键可回溯信息（文件路径、行号、错误码、断言、URL），输出纯文本，禁止调用工具，两阶段生成（`<analysis>` 草稿 → `<summary>` 正文，丢弃 analysis）。

**代价与风险**：更频繁的 LLM 调用（利用前缀缓存摊薄）；摘要后丢失未预料到的关键信息 → 模型可能重复调用工具。后者通过信息密度门槛与"保留可回溯锚点"缓解。

**结果形态**（决策 D6：原始内容默认落盘保留）：

```
<compressed-output>
工具结果已在线摘要。完整内容（80KB）已保存到：
{kdagent_dir}/sessions/{session_id}/tool-results/toolu_abc123.txt

摘要：
=== 测试运行结果 ===
PASS: TestUserCreate (0.02s)；FAIL: TestUserDelete (0.03s)
    expected: nil, got: permission denied
共 42 条用例，3 条失败，失败集中在 user 删除权限路径。

如需完整内容，用 ReadFile 按 offset/limit 读取。
</compressed-output>
```

**与 L1 的关系**：两者都在入口处预处理、原始内容都落盘可找回。区别：L1 给"前 2KB 预览"（零成本零损失，面向超大结果）；L2 给"语义摘要"（一次 LLM 调用，面向中等低密度结果），噪声更低、信息更浓缩。信息密度 HIGH 的结果不适用本层，直接原样写入。

### 5.4 L3：Auto-Compact（全量摘要）

**触发阈值推导**（以 200K 窗口为例，参数化通用）：

```
AUTO_COMPACT_TRIGGER = window - SUMMARY_OUTPUT_RESERVE - SAFETY_MARGIN
  = 200,000 - 20,000 - 13,000 = 167,000
```

- **SUMMARY_OUTPUT_RESERVE = 20K**：摘要本身要占空间。下限来自摘要需求（9 部分 + analysis 草稿 ≈ 15–18K），上限来自有效窗口压力（预留越大触发越早，且模型不会因空间大就写更长摘要）。
- **SAFETY_MARGIN = 13K**：覆盖"两次检查之间盲区"——检查点在每轮 API 前，一轮内并行工具可能新增多个大结果。固定值而非百分比，因为 buffer 防的是"单轮波动"（单次工具结果大小固定），与窗口总大小无关。
- **固定值 vs 百分比**：百分比在 200K 窗口"90% 触发浪费 / 98% 触发撞墙"，固定值 33K 在任何窗口下恰好挡住 1–2 次大工具调用。1M 窗口 → 967K 触发，buffer 仍 33K。

**摘要 Prompt**：9 个结构化部分——①主要请求和意图 ②关键技术概念 ③文件和代码段（关键代码片段保留）④错误和修复 ⑤问题解决过程 ⑥**所有用户消息（原文保留！）** ⑦待办任务 ⑧当前工作（最详细）⑨可能的下一步。

- 第 6 条为什么原文保留：用户原始表述包含意图、偏好、语气。改写会失真（"不要用 interface{}，用 any" 被摘要成 "偏好现代语法" 会引错）。
- **两阶段生成**：先 `<analysis>` 草稿梳理 → 再 `<summary>` 正文；analysis 丢弃。
- **禁止工具调用**：摘要调用保留 tools 参数（保持前缀与正常请求一致以命中缓存），但 Prompt 开头 + 结尾两头堵禁令（"只输出纯文本 / 工具调用会被拒绝"），且代码只读取文本输出，忽略工具调用事件。

**压缩后恢复**：
- 保留**近期原文**：从尾部按 token 回数，最近 `RECENT_KEEP`（10K token）或至少 5 条消息；**不从中切断 tool_use/tool_result 配对**。
- 重附被摘要掉的关键上下文：最近访问的文件（最多 5 个，每个 ≤5K token）+ 已激活 Skill 定义（总预算 25K token）+ **当前 todo 快照**（`12`：压缩后 todo 认知过期会导致检查点对表失真；快照独立重灌，不依赖摘要保留）。
- 摘要、会话记录路径、恢复文件快照拼在**同一条 user 消息**（用 `---` 分隔），之后紧跟保留的近期原文。
- **会话记录路径**防止模型编造：摘要里"修复了 handler.py"，模型想引用细节须去读会话记录或重新 ReadFile。

### 5.5 三层协作决策流程

```
工具结果返回
  │
  ├─ X ≥ 落盘阈值 ──────────────→ L1 落盘（预览+路径，零成本）
  ├─ X ≥ 在线压缩阈值 且 低密度 且 经济性通过 → L2 在线摘要（摘要写入）
  └─ 其他 ────────────────────→ 原样写入（写入即终态）

每轮 API 调用前：
  ├─ usage ≥ FORCE_COMPACT_LINE(177K) → 强制压缩（优先级最高）
  ├─ usage ≥ AUTO_COMPACT_TRIGGER(167K) 且 未熔断 → L3 Auto-Compact
  └─ 其他 → 正常调用

API 返回 prompt_too_long → 紧急压缩 → 重试原请求（仍超限则按正常错误处理）
```

## 6. 兜底保障与失败恢复

| 机制 | 触发 | 动作 |
|---|---|---|
| **强制压缩线** | usage ≥ `FORCE_COMPACT_LINE`（窗口 - 33K - 3K，200K 窗口=177K） | 无视熔断状态直接 ForceCompact；检查在熔断判断之前，优先级最高 |
| **紧急压缩** | API 返回 prompt_too_long | 捕获 → 立即 ForceCompact → 用新消息列表重试原请求 |
| **熔断** | L3 连续失败 3 次 | 停止自动触发，让用户手动处理（避免"压缩失败→重试→再失败"死循环） |
| **摘要请求超长** | 摘要请求本身 Prompt Too Long | 按 API 轮次分组 → 丢弃最旧几组 → 重试（最多 3 次）→ 仍不行丢 20% 消息组再试 |

### 6.1 触发逻辑：主循环视角（if-else 伪代码）

```python
def loop_iteration():
    # ── 阶段 A：调 API 之前（预防性）─────────────────────────
    usage = history.estimate_tokens(last_usage)      # P4：锚定上次真实用量

    if usage >= FORCE_COMPACT_LINE:                  # ① 强制压缩线（177K）：保底，最高优先级
        if force_fail < FORCE_FAIL_LIMIT:            #    force 独立预算，不受 auto 熔断影响
            force_compact()
        else:
            raise ContextFullError()                 #    force 连续失败达上限 → 不再徒劳，报错给用户
    elif usage >= AUTO_COMPACT_TRIGGER:              # ② 自动压缩线（167K）：常规预防
        if not circuit_open:                         #    auto 熔断只关自动路径（风险由 177K 兜底）
            auto_compact()
    # else: 未超限 → 正常继续

    # ── 阶段 B：正常调用 API ────────────────────────────────
    try:
        return llm.call(assemble_payload(...))
    except PromptTooLongError:                       # ③ 紧急压缩：撞墙后自救
        if force_fail < FORCE_FAIL_LIMIT:
            force_compact()                          #    压完重试原请求
            return llm.call(assemble_payload(...))
        raise ContextFullError()                     #    已无法自救 → 报错


def auto_compact():
    """常规预防。auto 独立预算，连续失败达上限 → 熔断（只关自动路径）。"""
    try:
        compactor.compact(history)
        auto_fail = 0
        force_fail = 0        # 压缩可行 → 两条预算都恢复
        circuit_open = False
    except Exception:
        auto_fail += 1
        if auto_fail >= AUTO_FAIL_LIMIT:
            circuit_open = True                      # 熔断：后续轮次不再自动压缩

def force_compact():
    """保底。force 独立预算，连续失败达上限 → 彻底认输报错。"""
    try:
        compactor.compact(history)
        force_fail = 0
        auto_fail = 0         # 压缩可行 → 两条预算都恢复
        circuit_open = False
    except Exception:
        force_fail += 1
        if force_fail >= FORCE_FAIL_LIMIT:
            raise ContextFullError()                 # 交给用户手动处理
```

**三个机制的定位与顺序**：
- **自动压缩**（167K，调 API 前）：常规手段，主动预防。
- **强制压缩**（177K，调 API 前）：保底防线，**无视熔断**——熔断只关闭"自动路径"，177K 是硬性底线，宁可再试一次。
- **紧急压缩**（prompt_too_long，调 API 后）：最后自救，压完重试原请求一次。
- **失败计数（独立预算）**：`auto_fail` 与 `force_fail` 各自独立（各 3 次）。auto 连续失败 3 次 → 熔断（只关自动路径）；**force 连续失败 3 次 → 抛 `ContextFullError` 报错给用户**（提示手动 /compact 或清理会话）。任何一次压缩成功 → 两个计数清零、熔断复位。关键性质：**auto 熔断不影响 force 的机会**——force 永远拥有自己完整的 3 次预算，只是触发时机更晚（177K / 撞墙）。这修正了 MewCode 无 force 上限的疏漏，同时避免共享计数"auto 用光预算、force 形同虚设"的问题。

## 7. 手动触发 /compact

- **预防性压缩**：用户已知接下来要读大量文件，提前腾空间。
- **话题切换**：从 bug A 切到 bug B，清理 A 的细节降噪。
- 与自动压缩共用同一套 L3 逻辑，仅触发方式不同。

### 9.2 标定机制（依赖阶段 3 可观测性）

经济性模型与若干阈值依赖真实任务数据，落地后在可观测性基建上统计：
1. **P 增长速度**：上下文在典型任务中每轮增长多少 token → 决定一个窗口内平均轮数。
2. **X 长度分布**：工具结果的 token 分布 → 校准 `ONLINE_COMPRESS_MIN` 与落盘阈值。
3. **实际压缩率**：导出工具结果分析平均 α，按类型分类 → 校准 `EXPECTED_RATIO_BY_TYPE`。
4. **SAFETY_MARGIN**：统计单轮最大新增量 → 校准 13K。
