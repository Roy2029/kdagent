# Coding Agent 技术规格 · 02 核心引擎（LLM provider / 对话管理器 / ReAct Loop）

> 状态：**已确认 v0.2**（2026-08-11）｜里程碑：阶段 2（能跑档）｜依赖：`01`（上下文工程）｜被依赖：`03` 工具系统（Loop 调用工具）、`04` 会话管理（历史持久化）、`05` 交互与 TUI（消费事件流）

---

## 1. 目标与范围

**本模块是 Agent 的心脏**。它回答：模型怎么被调用、消息怎么被构造、Agent 怎么自主工作下去。

- **LLM Provider 抽象**：屏蔽不同供应商协议差异，暴露统一领域语义。上层只认自己的类型，换模型改配置文件、代码零改动。
- **对话管理器**：把消息构造的规矩收在一个地方（角色交替、tool_use/tool_result 配对、id 一一对应），给后续压缩/回滚留统一入口。
- **ReAct Loop**：一个 while 循环持续调 LLM 并拼接上下文，直到模型不再请求工具——让 Agent"自己干活"。

**不在本模块范围**：
- 系统 Prompt 具体文案（七模块）→ 本模块只引用 `01` 的组装管线与 Plan Mode 指令槽位
- 工具的实现与描述 → `03` 工具系统（本模块只调用 `ToolRegistry` 与 `is_concurrency_safe`）
- 上下文压缩机制 → `01`（本模块在压缩检查点调用 `ContextManager.check_before_call`）
- 会话持久化/恢复 → `04`（本模块只保证"内存中的历史合法"，落盘由 `04` 负责）

## 2. 与相邻模块关系

```
        ┌──────────────┐   AgentEvent 事件流   ┌──────────────┐
        │  05 交互/TUI │ ◀──────────────────── │  02 Agent   │
        └──────────────┘                      └──────┬───────┘
                                                     │ 写路径：规范化消息
        ┌──────────────┐   读路径：组装/压缩   ┌─────▼─────┐
        │  01 上下文工程│ ◀──────────────────── │ ConversationManager │
        │ ContextManager│                      └─────┬─────┘
        └──────────────┘                            │ 工具调用
        ┌──────────────┐   ToolRegistry       ┌─────▼─────┐
        │  03 工具系统  │ ◀──────────────────── │  ReAct Loop │
        └──────────────┘                      └───────────┘
```

- **依赖 `01`**：`Payload` 组装（`assemble_payload`）、token 估算（`estimate_tokens`）、压缩检查（`check_before_call`）、入口压缩（`on_tool_result`）。本模块是 `01` 的第一消费方。
- **被 `05` 依赖**：Agent 只产出 `AgentEvent` 异步流，UI 消费即渲染；Agent 不感知 UI 存在。
- **与 `04` 协作**：`04` 持久化本模块维护的历史、并在恢复时用 `ConversationManager.repair_chain` 修复消息链。

## 3. 详细设计

### 3.1 消息模型（领域类型）

所有 provider 差异被挡在 adapter 里，上层只见统一类型。**响应里 content 永远是数组**——一次回复可能是 text + 多个 tool_use。

```python
# engine/messages.py
from typing import Literal, TypeAlias
from dataclasses import dataclass, field

@dataclass
class TextBlock:
    text: str

@dataclass
class ThinkingBlock:          # Extended Thinking
    thinking: str
    signature: str | None     # 带签名必须原样回传，不能丢（见 §3.5）

@dataclass
class ToolUseBlock:
    id: str                   # 唯一标识，与 ToolResultBlock 配对
    name: str
    input: dict

@dataclass
class ToolResultBlock:
    tool_use_id: str          # 对应 ToolUseBlock.id
    content: str
    is_error: bool = False

ContentBlock: TypeAlias = TextBlock | ThinkingBlock | ToolUseBlock | ToolResultBlock

@dataclass
class Message:
    role: Literal["user", "assistant"]
    content: list[ContentBlock]
```

**两条铁律**（adapter 之外、领域层也要守的语义约定）：
1. **工具结果以 user 身份回传**。API 视角"所有你发给模型的归 user"。tool_result 若错挂 assistant，两条 assistant 相连，API 直接拒收（`roles must alternate`）。
2. **assistant 的 text 与 tool_use 不拆开**。模型一次回复（一段话 + 调 2 个工具）是**一条** assistant 消息，不能拆成两条。

### 3.2 LLM Provider 抽象层

**核心原则：暴露领域语义、隐藏 SDK 细节**。定义自己的类型，把各家 SDK 关在各自 adapter 里——不要指望写一个通用函数揉合所有供应商规则（Anthropic 把 system 提为顶层参数、OpenAI 兼容把 system 放 messages[0] 且 tool_result 是独立 role，规则完全不同）。

```python
# engine/llm/base.py
@dataclass
class ProviderConfig:
    protocol: Literal["anthropic", "openai"]   # 分发到对应 adapter
    model: str
    base_url: str | None = None                 # 默认官方端点
    api_key: str = ""                           # 从环境变量读取，不进代码

@dataclass
class ToolSchema:                               # 领域级工具描述
    name: str
    description: str
    input_schema: dict

@dataclass
class Payload:
    system: str
    messages: list[Message]
    tools: list[ToolSchema]
    max_tokens: int

# 高层流式事件（adapter 把各家的 SSE 序列翻译成这 5 种）
@dataclass
class LLMStreamEvent:
    type: Literal["text_delta", "tool_use", "usage", "stop", "error"]
    text: str | None = None
    tool_use: ToolUseBlock | None = None
    usage: Usage | None = None
    stop_reason: str | None = None
    error: Exception | None = None

class LLMClient(Protocol):
    async def stream_chat(self, payload: Payload) -> AsyncIterator[LLMStreamEvent]:
        ...
```

**adapter 翻译清单**（每接一家新增一份 adapter，差异全关在自己那份里）：

| 差异点 | Anthropic Messages | OpenAI 兼容（覆盖 DeepSeek/Kimi/Qwen/GLM） |
|---|---|---|
| system | 顶层参数 | `messages[0]`（role=system） |
| tool_result | user 消息里的 `tool_result` block | 独立 `role: tool` 消息（`tool_call_id` 对应） |
| tool_use | assistant 消息里的 `tool_use` block | assistant 消息的 `tool_calls` 数组 |
| thinking | `thinking` block（带 signature） | 无（或 `reasoning_content` 变体） |
| 相邻同角色消息 | API 自动合并 | 需客户端自行合并 |
| 流式 | SSE：`message_start → content_block_* → message_delta → message_stop` | SSE：`data: [DONE]` 终止 |

**Usage 复用 `01` 的模型**：`message_start` 带 `input_tokens`、`message_delta` 带 `output_tokens`，累计得到缓存命中等字段。`01` P4 的"锚定上次真实用量"就靠这里回填。

**token 估算锚点（`01` P4 的落实点）**：每次响应后记录 `Usage`；下轮 `history.estimate_tokens(last_usage)` 用它当基准、只估增量。

### 3.3 对话管理器（ConversationManager）

**写路径唯一入口**。引擎层任何产生消息的动作都必须经由它，消息构造规矩只在一处维护。

**与 `01` 的分工**：`01` 的 `ConversationHistory`（存储/token 估算）与 `ContextManager`（组装/压缩）是"读路径"；本模块的 `ConversationManager` 是"写路径"——把引擎动作规范化为合法消息，再交给 `01` 落库。

```python
# engine/conversation.py
class ConversationManager:
    """语义化 add 方法；内部保证结构合法，再委托 01 落库。"""

    def __init__(self, history: ConversationHistory, context: ContextManager): ...

    def add_user_message(self, text: str, extra_blocks: list[ContentBlock] | None = None) -> None:
        # 用户输入 + 动态注入（system-reminder，见 01 §4.2）合并为一条 user 消息
        # 满足交替规则；相邻 user 块在序列化层自动合并

    def add_assistant_message(self, blocks: list[ContentBlock]) -> None:
        # 模型完整回复（text + tool_use + thinking）作为一条 assistant 消息
        # append-only，写入即终态（01 P2）

    def add_tool_results(self, results: list[ToolResult]) -> None:
        # ① 每个结果先过 context.on_tool_result()（L1 落盘 / L2 在线摘要，见 01 §5）
        # ② 组装为 ToolResultBlock（tool_use_id 一一对应）
        # ③ 全部挂在一条 user 消息下 append（is_error=True 也照常写入，模型下轮自行调整）

    def last_tool_use_ids(self) -> list[str]:
        # 校验配对用：返回最近一条 assistant 消息里的 tool_use id 集合

    def repair_chain(self) -> None:
        # 04 会话恢复时调用：补缺失的 tool_result、剔除孤立块、保证交替合法
```

**为什么需要它**：消息构造的规矩散落各处手写迟早写错（拼错角色 → API 拒收；id 对不上 → 本轮接不上）。收在管理器里后，压缩（`01`）把一段历史换成摘要、回滚（`04`）截断历史，都只是给管理器多几个方法的事。

### 3.4 ReAct Loop

ReAct = 推理（Think）→ 行动（Act）→ 观察（Observe）交替。Claude API 原生映射：text=Think、tool_use=Act、tool_result=Observe，无需发明新格式。

```python
# engine/agent.py
MAX_ITERATIONS = 50           # 安全网，正常编码任务很少超过

class Agent:
    def __init__(self, config, llm: LLMClient, conversation: ConversationManager,
                 context: ContextManager, tools: ToolRegistry, events: AgentEventSink): ...

    async def run(self, user_input: str) -> None:
        conversation.add_user_message(user_input)
        for turn in range(MAX_ITERATIONS):
            try:
                status = await self._loop_iteration()
            except asyncio.CancelledError:          # 用户 Esc / Ctrl+C
                self._flush_partial_to_history()    # 已收部分落成一条消息，不丢
                events.emit(CancelledEvent())
                return
            if status is TERMINAL:
                return
        events.emit(MaxIterationsReachedEvent())

    async def _loop_iteration(self) -> AgentStatus:
        # ── 前置：压缩检查（01）──
        usage = conversation.history.estimate_tokens(self._last_usage)   # P4 锚定真实用量
        context.check_before_call(usage)                                  # 可能触发 L3 压缩

        # ── 调 LLM：流式消费 → 聚合成完整响应 ──
        payload = context.assemble_payload(config, conversation.history)
        blocks, stop_reason = [], None
        try:
            async for ev in llm.stream_chat(payload):
                if ev.type == "text_delta":   events.emit(StreamTextEvent(ev.text))
                elif ev.type == "tool_use":   blocks.append(ev.tool_use)
                elif ev.type == "usage":      self._last_usage = ev.usage; events.emit(UsageEvent(ev.usage))
                elif ev.type == "stop":       stop_reason = ev.stop_reason
                elif ev.type == "error":      raise ev.error
        except PromptTooLongError:             # 01 紧急压缩自救
            context.emergency_compact(conversation.history)
            return CONTINUE                    # 重试下一轮

        # ── 分类：有 tool_use 继续，否则终止 ──
        if self._has_tool_use(blocks):
            conversation.add_assistant_message(blocks)
            batches = partition_tool_calls(blocks, self.tools)
            for batch in batches:
                results = await self._execute_batch(batch)    # 并发/串行
                conversation.add_tool_results(results)         # 02 规范 + 01 入口处理
            events.emit(TurnCompleteEvent(turn=self._turn))
            return CONTINUE
        else:
            conversation.add_assistant_message(blocks)
            events.emit(LoopCompleteEvent(turns=self._turn + 1, usage=self._last_usage))
            return TERMINAL
```

### 3.5 状态机：每轮只有两条路（预留扩展）

```python
AgentStatus = Literal["CONTINUE", "TERMINAL", "NEED_CONFIRM", "RATE_LIMITED"]
```

能跑档只走 CONTINUE/TERMINAL；把分类逻辑集中一处，后续加 NEED_CONFIRM（`06` 权限 HITL）、RATE_LIMITED（限流退避）只是加分支。

**四种停止条件，缺一不可**：
| # | 条件 | 机制 |
|---|---|---|
| 1 | 模型主动完成 | `stop_reason == end_turn` 且无 tool_use |
| 2 | 迭代上限 | 50 次强制停止，提示用户 |
| 3 | 用户取消 | Esc 中断当前循环（程序不退，可继续输入）；Ctrl+C 才退出进程 |
| 4 | 异常状态 | 工具不存在/被禁 → **返回 errorResult 进历史**（不终止循环），模型下轮自行调整 |

**断路器（连续失败挂起，第五道保险）**：Loop 维护连续失败计数——工具执行返回 `is_error=True` 或 `TestingEvent=test_failed/regression_detected`（`12` 测试闭环）连续累加，任一轮成功即清零。连续达 `CIRCUIT_BREAK_LIMIT`（3 次，初值）→ 挂起自动重试，状态机置 `CIRCUIT_OPEN`，注入 system-reminder「已连续失败 3 次，需重新评估策略」；模型给出新的行动计划后复位。**防无限重试烧 token**，对齐 `12` §3.5/§3.8。与 §3.9 的单次错误重试（RateLimit 退避）互补：重试管「暂时性故障」，断路器管「策略性失败」。

**Extended Thinking**：开启后响应的 `thinking` block 排在 text 前。**带工具调用的那一轮，thinking 连同签名必须原样回传**（签名加密完整思考内容，服务端靠它验证并还原推理上下文）——不能当草稿丢。纯聊天轮次可以不回传。thinking 计入 `output_tokens`，是有成本的；Agent 场景通常值得（一次准确调用省好几轮纠错）。

### 3.6 事件流 AgentEvent（与 UI 完全解耦）

Agent 的输出是一个 `AgentEvent` 异步流，UI 是消费者。Agent 不知道 UI 长什么样，换 Web 界面/纯 JSON 输出，Agent 零改动。

| 事件 | 含义 | 携带数据 |
|---|---|---|
| `StreamTextEvent` | 模型正在输出的文字增量 | 一小段文本 |
| `ToolUseEvent` | 模型请求调用工具 | 工具名、输入、id |
| `ToolResultEvent` | 工具执行完成 | 结果、是否出错、耗时 |
| `TestingEvent` | 测试闭环事件（`12` TestRunner 产出） | `passed` / `failed` / `regression_detected` + 失败归因信息（失败测试名/断言/栈/diff） |
| `TurnCompleteEvent` | 一轮 LLM 调用完成 | 轮次序号 |
| `LoopCompleteEvent` | 整个循环结束 | 总轮次、累计 usage |
| `UsageEvent` | token 用量更新 | 累计输入/输出 |
| `ErrorEvent` / `CancelledEvent` / `MaxIterationsReachedEvent` | 异常/中断/超限 | 错误信息 |

**流式与历史的解耦**（`01` append-only 的配套）：流式片段进缓冲区、UI 实时渲染，**历史不动**；本轮结束缓冲区完整文本才落成一条 assistant 消息。中断时已收部分照常落成一条消息，不碎、不丢。

### 3.7 工具分批执行

模型一次可能返回多个 tool_use。按 `is_concurrency_safe` 划分并发批与串行批，安全工具并行、写操作隔离，无需依赖检测。

```python
def partition_tool_calls(tool_uses, registry) -> list[Batch]:
    batches = []
    for tc in tool_uses:
        tool = registry.get(tc.name)
        safe = tool is not None and tool.is_concurrency_safe(tc.input)
        if safe and batches and batches[-1].is_concurrency_safe:
            batches[-1].calls.append(tc)
        else:
            batches.append(Batch(is_concurrency_safe=safe, calls=[tc]))
    return batches

# 例：[Read, Read, Edit, Read, Read] → [Read,Read]并发 | [Edit]串行 | [Read,Read]并发
```

- **并发批**：`asyncio.gather` + 并发上限 `CONCURRENCY_LIMIT`（防无限并发拖垮系统）。
- **串行批**：逐个执行。
- **单工具执行**：`_exec_one` 统一捕获异常 → 产出 `ToolResult(ok=False, error=...)`，不让单个失败打断整轮。

### 3.8 Plan Mode

**只想不做**。实现核心是 **Prompt 指令约束**，而非禁写工具——规划阶段经常要跑 `grep -r TODO .`、`find . -name "*.go"` 等只读 Bash，硬禁会拖垮探索效率。

- `01` 的 `assemble_system_prompt` 预留 `PLAN_MODE_INSTRUCTIONS` 槽位：注入强指令（"不得修改任何文件，唯一可写的是指定 plan file"）。
- 权限矩阵不变（read=allow, write=ask, command=ask）；唯一特殊处理是 **plan 文件自动放行**。
- 若 LLM 不听约束尝试写非 plan 文件 → 走正常权限确认（`06`），由用户裁决。
- **能跑档先落 prompt 约束层**；权限兜底依赖 `06`（可控档），届时补齐。

### 3.9 错误处理与重试

provider 层错误分类，各自策略：

| 错误 | 处理 |
|---|---|
| `RateLimitError` | 状态机置 `RATE_LIMITED`：指数退避 + jitter（0.5s→1s→2s，上限 30s），重试 |
| `TimeoutError` / `ConnectionError` | 重试 2–3 次（临时故障），仍失败 → `ErrorEvent` 上报 |
| `PromptTooLongError` | 交给 `01` 紧急压缩（force_compact + 重试原请求） |
| `AuthError` | 直接上报，不重试（配置问题，重试无意义） |
| 工具不存在/执行失败 | `errorResult` 进历史，不终止循环 |

**重试与压缩的预算交互**（对齐 `01` §6.1 独立预算）：重试不计入 `auto_fail/force_fail`；但压缩失败计数在 `01` 侧管理，本模块只触发、不管计数。

## 5. 验收标准

- [ ] 流式调用 Anthropic API 成功，`text_delta` 逐字到达（TUI 可渲染）；`usage` 正确回填
- [ ] 单轮对话 user/assistant 交替合法，API 不拒收
- [ ] 工具结果以 user 身份回传、id 一一对应；连续两条 assistant 不出现
- [ ] ReAct Loop 自主完成 5–6 步任务（如"写 HTTP 服务器并编译通过"），无需人工逐步催
- [ ] 四种停止条件各自生效：end_turn 自然收尾 / 50 次上限强制停 / Esc 干净退出 / 工具不存在返回 errorResult
- [ ] 并行分批：[Read, Read, Edit, Read, Read] 拆成三批，Edit 不与 Read 同批
- [ ] 切换 provider（Anthropic ↔ OpenAI 兼容）上层代码零改动，仅改 `ProviderConfig`
- [ ] Plan Mode 下只读探索 + 写 plan 文件成功；尝试写非 plan 文件被权限系统拦截（标注：完整版依赖 `06`）
- [ ] Extended Thinking 带工具调用轮次，thinking 块原样回传不报错
- [ ] 模拟 RateLimit → 退避重试成功；模拟 PromptTooLong → 走 `01` 紧急压缩后重试成功
- [ ] `TestingEvent` 进事件流：`12` TestRunner 产出 passed/failed/regression_detected，`05` 可渲染"正在跑测试…"
- [ ] 断路器：连续 3 次工具/测试失败 → 挂起并注入 system-reminder，模型给出新计划后复位，不无限重试
