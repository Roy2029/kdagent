# 记忆系统

参考 ClaudeCode 和 OpenClaw 的记忆系统，主要有三个组成部分：**静默读写、主动读写、Auto-Dreaming**。


# 算法思路

## 静默读写

静默读写扮演的角色是用户零感知的情况下，自动从对话中提取可长期复用的关键信息，并在会话时自动加载到上下文中。

### 读：会话开始时如何加载记忆

- **通用思路**：新会话开始时，从记忆中召回若干条最相关的记忆条目组装到上下文中。
- [**OpenClaw 实践**]：会话启动时**整体注入** `MEMORY.md`（以及 SOUL.md / AGENTS.md 等引导文件）到 system prompt，而非语义召回。设计要点：
  - `MEMORY.md` 是经过 Dreaming 治理的"精华文件"，直接全量注入（有 ~12KB 单文件上限）。
  - 这种"注入式静默读"与"召回式静默读"是两种设计哲学。注入式的代价是文件必须小且有预算上限；召回式的代价是每会话一次检索成本。
  - 语义召回不在这里做，而是交给主动线的 `memory_search`（见下）。
- [**ClaudeCode 实践**]：Claude Code 与 OpenClaw 相反，走的是**"召回式静默读"**，且召回引擎是 **LLM side-query 而非向量检索**：
  - **记忆使用说明注入系统提示词**（`loadMemoryPrompt`）：注入的不是 MEMORY.md 内容，而是"如何使用记忆"的指令——四类分类法（user/feedback/project/reference）、两步保存法、何时访问、如何信任回忆。相当于把"记忆使用手册"常驻系统提示词，而非把"记忆本身"常驻。
  - **Memory Prefetch（真正的内容召回）**：每回合开始异步执行——扫描记忆目录（≤200 个 .md，按 mtime 降序）→ 用小型 Sonnet 模型从"文件名 + frontmatter 的 description"清单里选出最相关的 Top 5 → 读取并截断 → 在工具执行完成后注入为 `<system-reminder>` 附件喂给下一轮。
  - 选型要点：**用 LLM 当检索器，省掉 embedding / 向量索引整条基础设施**。召回质量取决于 description 字段写得好不好；成本是每回合一次 side-query（Sonnet 选 5 条），但它与模型流式输出并行跑，用户几乎无感。未结算时本轮零等待跳过、下轮重试，不阻塞主流程。
  - 与 OpenClaw 对比：OpenClaw 是"启动时注入治理好的精华文件"（离线治理、启动便宜、内容固定）；Claude Code 是"在线语义召回"（每回合检索、更贴当前问题、但每次多一次 LLM 调用）。两者共同点：**都避免把整个记忆库塞进上下文**。

### 写：什么时机自动提取

- **通用思路**：每经过一定对话轮次或上下文 token 阈值，触发一次后台异步自动提取。需要 LLM 组件做智能处理。
- [**OpenClaw 实践**]：静默写在 OpenClaw 里有三个子机制：

| 子机制 | 触发条件 | 是否消耗 LLM | 写入目标 |
|--------|---------|-------------|---------|
| **Flush（半主动）** | 会话 tokens 接近模型窗口上限，且本压缩周期内未 flush | 是（一次完整 LLM 回合） | `memory/YYYY-MM-DD.md` |
| **索引同步（纯静默）** | chokidar 监听 `memory/*.md` 变更，防抖后增量同步 | 否（机械分块+embedding） | SQLite 检索引擎 |
| **召回追踪（纯静默）** | 每次 `memory_search` 执行后 | 否 | 短期召回存储 |

  - **Flush 是"半主动"**：虽然用户无感知，但它消耗一次完整 LLM 调用（系统在压缩前发起"写下记忆"的回复回合，让 LLM 判断什么值得记）。
  - **召回追踪是关键设计**：`memory_search` 每次执行时，系统自动记录"哪个片段被哪个查询召回了"（`queueShortTermRecallTracking`）。这形成了 **主动线 → Dreaming 线** 的信号管道。检索不仅是消费记忆，还在生产记忆信号。
- [**ClaudeCode 实践**]：静默写在 Claude Code 里有三个子机制，全部后台执行：

| 子机制 | 触发条件 | 是否消耗 LLM | 写入目标 |
|--------|---------|-------------|---------|
| **extractMemories（纯静默）** | 每回合末（无工具调用的收尾轮，`handleStopHooks` 内） | 是（fork 代理，maxTurns=5） | `~/.claude/projects/{项目}/memory/` 主题文件 + MEMORY.md 索引行 |
| **SessionMemory（纯静默）** | 每次模型采样完成后（post-sampling hook） | 是（fork 代理，只允许编辑该一个文件） | `{项目}/{会话}/session-memory/summary.md` |
| **主代理直接写（半主动）** | 模型自己决定（系统提示词引导"两步保存法"） | 无额外成本 | 同上 memory 目录 |

  - 选型要点：
    - **后台提取一律用 fork 代理而非主代理**：不阻塞主循环、不污染主上下文；工具权限被收紧（只读 + 只读 Bash + auto-mem 目录内的 Edit/Write），安全性可控。
    - **主代理写与后台提取互斥**（`hasMemoryWritesSince`）：主代理本回合已写过记忆，后台提取器跳过该区间，避免重复劳动。
    - **写入频率自适应**：extractMemories 按合格回合节流（GrowthBook 控制）；SessionMemory 按 token 增量 + 工具调用数判断"是否到自然停顿点"，避免每轮都写。

## 主动读写

主动读写向 Agent 提供主动管理记忆的工具，Agent 可以主动或者在用户要求下，提炼信息并存储记忆，或召回相关的记忆进上下文。

- [**OpenClaw 实践**]：
  - **读工具**：`memory_search(query)`（混合检索）+ `memory_get(path)`（精确读取）。两个工具都支持 `corpus=memory|wiki|all|sessions` 过滤。
  - **没有专门的写工具**（无 memory_save）。Agent 写记忆走普通文件工具，写入 `memory/*.md`。
  - **System prompt 注入"Memory Recall"指引段**，告诉 Agent 何时应该搜索：
    > "在回答任何关于过往工作、决策、日期、人名、偏好、待办事项的问题之前：先对 MEMORY.md + memory/*.md 运行 memory_search，再用 memory_get 取需要的行。"
  - 关键洞察：OpenClaw 通过 **prompt 指引 + 工具暴露** 让 Agent 自己决定何时检索，而不是系统每轮强制召回。这样检索成本可控、目标明确。
- [**ClaudeCode 实践**]：Claude Code **不提供** `memory_search` / `memory_save` 这类专用记忆工具，主动线完全靠**通用文件工具 + 提示词引导**：
  - **读**：模型用普通 Read / Glob / Grep。系统提示词的记忆段告诉它：MEMORY.md 是索引 → 按索引找主题文件 → 读正文。
  - **写**：模型用普通 Write / Edit，遵循"两步保存法"（先写主题文件，再在 MEMORY.md 加一行索引）。
  - 选型要点：**工具面最小化**——不发明专用工具，记忆文件对模型和人类都是普通文件（人类可直接用编辑器查看/修改，git 可追踪）。检索时机的决策权完全交给模型，靠提示词引导"何时该翻记忆"。代价是检索质量依赖模型自觉；收益是零专用基建、文件生态开放。
  - 与 OpenClaw 对比：OpenClaw 的 `memory_search` 让检索结构化、可被召回追踪（自动喂给 Dreaming），但多一层工具抽象；Claude Code 用通用工具 + 模型自身判断，更简单，但**缺少"检索信号"的天然采集点**（也因此它的 Dream 没有召回追踪）。

## Auto-Dreaming

Dreaming 是一种对已有记忆数据进行治理的手段。对已有记忆进行去重合并、冲突消解。

- [**OpenClaw 实践**]：Dreaming 的本质是**信号驱动的记忆巩固**——不是简单的去重，而是"经常被召回的片段存活并升级"。
  - **定时触发**：托管 Cron 任务，默认每晚运行（配置 cron 表达式），通过 `before_agent_reply` 钩子检测触发。
  - **信号来源**（两路摄入）：
    1. `memory/*.md` 文件 → 解析分块 → 记录为召回条目
    2. 会话转录 → 增量读取新行 → 记录为召回条目
    3. （间接）`memory_search` 的召回追踪 → 记录"哪个片段被用了多少次"
  - **三阶段处理**（模拟人类睡眠周期）：
    1. **Light Sleep（浅睡）** — 摄入信号、去重、打分、暂存候选
    2. **REM Sleep（快速眼动）** — 跨候选找主题模式，筛选"候选真理"
    3. **Deep Dreaming（深度睡眠）** — 对候选多维度排名，Top-N 提升（promote）到 `MEMORY.md`
  - **提升的打分维度**：频率、相关性、多样性、近因性、跨天巩固度、概念覆盖度。通过阈值（如 minScore≥0.75、minRecallCount≥3、minUniqueQueries≥2）。
  - **预算控制**：`MEMORY.md` 上限 ~10KB，超限时删除最旧的自动提升段，用户手写内容永不删除。
  - 设计意图：让记忆**跟随使用强度自然分层**——高频使用的沉淀为长期记忆，低频的自然淘汰。
- [**ClaudeCode 实践**]：Claude Code 的 AutoDream 要简单得多——**单阶段 fork 代理整合**，没有三阶段睡眠模拟：
  - **触发门控**（`services/autoDream/autoDream.ts`，注释即 "Background memory consolidation"）：时间门（距上次整合 ≥24h）→ 会话门（mtime 更新的会话数 ≥5）→ 锁（无其他进程在整合）。任一不过则跳过。
  - **动作**：用 `/dream` 提示词 fork 一个代理，**读取多个会话的 transcript**，把分散的记忆融会贯通，写回 auto-mem 目录。工具集与 extractMemories 相同（只读 + 只写 auto-mem）。
  - 选型要点：Claude Code 把"什么值得记、如何合并冲突"的判断**全部委托给 LLM**（fork 代理自由发挥），而不是用启发式打分/排名规则。相比 OpenClaw 的六维打分（频率/相关性/多样性/近因性/跨天巩固度/概念覆盖度），Claude Code 更"笨"但更简单、更依赖模型能力。
  - ⚠️ 注意："Dream" 在 Claude Code 里还有另一层含义——**推测执行**（`IDLE_SPECULATION`，用户打字时预测下一次响应，用于延迟隐藏），它**不属于记忆系统**，是另一个子系统（PromptSuggestion）。

## 与上下文压缩的联动

触发上下文压缩时，压缩动作本质上是一种摘要提炼。

- [**OpenClaw 实践**]：压缩前会先执行一次 **Memory Flush**（见上"静默写"），保证值得记住的信息在上下文被压缩丢弃之前先落盘。这是"压缩=丢弃"与"记忆=保留"之间的桥梁。Flush 与压缩共用同一个 token 阈值判断（`shouldRunMemoryFlush`），同一压缩周期只 flush 一次。
- [**ClaudeCode 实践**]：联动方向相反，是"**压缩复用现成的记忆摘要**"而非"压缩前现场写"：
  - **SessionMemory ↔ AutoCompact**：自动压缩触发时，优先 `trySessionMemoryCompaction()`——直接用后台早已维护好的 `summary.md` 当压缩摘要，**省掉一次 LLM 压缩调用**。只有会话记忆不可用 / 为空 / 边界不可靠时，才回退到传统 `compactConversation()`（现场 fork 代理总结整段历史）。
  - **等待在途提取**：`waitForSessionMemoryExtraction()` 会等正在进行的 SessionMemory 提取完成，保证摘要新鲜。
  - 与 OpenClaw 对比：OpenClaw 是"压缩=丢弃，先 flush 保留"（压缩前现场写一次记忆）；Claude Code 是"摘要一直在维护，压缩时白嫖"（成本摊薄到每次采样后）。两者解决同一个问题：**别让有价值的对话内容随压缩一起丢失**。

# 存储方案

通常用 JSONL 存储对话历史原文。召回记忆方面：

- **OpenClaw**：采用 **混合存储**——Markdown 文件（源数据）+ SQLite 检索引擎（派生检索层）。
  - **源数据**：`memory/YYYY-MM-DD.md`（按日分桶）+ `MEMORY.md`（精华）+ `DREAMS.md`（梦境记录）。人类可读、可编辑，是"真相来源"。
  - **检索层**：SQLite（`memory-index.sqlite`），含 FTS5 全文索引 + sqlite-vec 向量索引 + embedding 缓存。从 Markdown 文件派生，可随时重建。
  - **信号层**：`memory/.dreams/` 下的 JSON 文件（短期召回存储、摄入进度、阶段信号）。
  - 设计要点：**源数据与检索层分离**。检索层是派生的、可丢弃的；源数据是可读可编辑的。索引损坏时重建即可，不会丢记忆。
- **ClaudeCode**：纯 Markdown 文件方案，无任何独立检索层：
  - **源数据**：`~/.claude/projects/{项目}/memory/` 下的主题文件（frontmatter 含 `name/description/type`）+ `MEMORY.md`（纯索引，截断上限 200 行 / 25KB）。
  - **分类**：四类 taxonom——user（关于用户）/ feedback（行为偏好）/ project（项目约束）/ reference（外部资源）。分类影响模型的记忆维护策略。
  - **检索层 = LLM 本身**：没有向量索引。静默召回靠 Sonnet side-query 从"描述清单"里选 Top5；主动读靠模型自己翻索引。
  - **会话记忆**：`{项目}/{会话}/session-memory/summary.md`（跨会话摘要，供压缩复用）。
  - **对话原文**：`~/.claude/projects/{项目}/{会话}.jsonl`（append-only JSONL，每条消息一行，靠 `parentUuid` 链重建）。
  - 选型要点：**把"检索"这件基础设施整个省掉，换成一次 LLM 调用**。优点：零索引维护、文件人类可读可编辑、git 可追踪；缺点：记忆量大（>200 文件）时 side-query 的清单就开始失真，缺少可扩展的上限。

## OpenClaw三条线的闭环

```
        ┌─────────────────────────── 静默读（注入 MEMORY.md） ───────────────────────────┐
        │                                                                               │
        ▼                                                                               │
   ┌──────────┐   Flush(半主动写)   ┌────────────────┐  索引同步(静默写)  ┌──────────────┐
   │ 用户会话  │ ─────────────────→ │ memory/*.md 文件 │ ───────────────→ │ SQLite 检索引擎 │
   └──────────┘                     └───────┬────────┘                   └──────┬───────┘
        ▲                                   │ 摄入                                │ 检索
        │                                   ▼                                    ▼
        │                           ┌──────────────┐                    ┌────────────────┐
        │                           │  Auto-Dreaming │                    │ 主动线          │
        │                           │ 短期召回存储   │ ←──召回追踪──────── │ memory_search   │
        │                           │ 三阶段巩固     │                    │ memory_get      │
        │                           └───────┬──────┘                    └────────────────┘
        │                                   │ Promote
        │                                   ▼
        │                            ┌──────────────┐
        └────────────────────────────│   MEMORY.md  │
               静默注入（新会话启动）   └──────────────┘
```

关键交接点：
1. **检索消费即信号生产**：主动线的 `memory_search` 每次执行都自动记录召回信号 → 喂给 Dreaming
2. **文件是唯一真相来源**：Flush 写入、索引读取、Dreaming 摄入，都围绕 `memory/*.md` 这一层
3. **MEMORY.md 是两线的汇合点**：Dreaming 写入它，静默读注入它

> **Claude Code 的闭环对照**：Claude Code 的三条线比 OpenClaw 更简单，且缺少"召回追踪"这个信号管道——
> - 静默读 = Memory Prefetch（LLM 召回 Top5）+ 记忆使用说明注入；静默写 = extractMemories + SessionMemory + 主代理直接写。
> - 主动读/写 = 通用文件工具 + 提示词引导（无专用 `memory_search` / `memory_save`）。
> - Dream = 单阶段 fork 代理跨会话整合（无三阶段、无打分、无召回追踪）。
> - 因此 Claude Code 的闭环是"文件 ↔ LLM"的扁平结构，没有 OpenClaw 的"信号 → 巩固 → 提升"反馈环。取舍本质：**OpenClaw 用更多工程换取记忆治理的可控性；Claude Code 用 LLM 能力换取实现简单**。
