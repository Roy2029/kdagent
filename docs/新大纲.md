# 蓝图
## 总体编排
项目以claude code最佳实践为参考蓝本，纵向分为6个可交付版本，横向有3条持续升级的主线。
### 版本零：Chatbot
三个内容：
- LLM provider配置
- ReAct loop + 对话历史
- 流式响应前端
### 版本一：能行动的智能体
从此版本开始将围绕三条主线逐步升级：记忆系统、工具能力、可观测性
- 记忆：会话管理
- 工具：工具系统
- 可观测性：日志
### 版本二：长程、受约束、可回溯的Agent
- 记忆：上下文压缩
- 工具：权限系统与hook
- 可观测性：trace
### 版本三：自动记忆系统、工具生态、完整可观测性
- 记忆：静默记忆系统
- 工具：mcp
- 可观测性：监控
### 版本四：高性能可量化Agent框架
- 记忆：主动记忆系统
- 工具：skill系统
- 可观测性：评估
### 版本五：高可靠
三大主线基本建设完成。开发更高级的功能。
- subagent & worktree
- Agent harness

## 板块设计描述
### 整体设计理念
#### Agent=LLM + runtime + Harness
Agent大致可以拆成三个部分：LLM作为智能的来源，runtime为其套上一层可交互的软件基础，harness则通过进一步的规则和约束为LLM的不确定性赋予可靠性与稳定性。
一家之言：学明白了上下文窗口的生命周期，就学明白了AGENT设计。不论是最基础的消息格式、LLM响应、工具调用，还是上下文压缩、记忆系统，上下文都是贯穿始终的时序线索。
为什么分成记忆、工具和可观测性三条主线？从我个人的学习历程看，这是三个高内聚且重要的模块，能够很好地由上下文生命周期联系起来；从模块之间的属性和依赖看，记忆和工具这两个主题基本能覆盖一个完整AGENT的所有关键设计，而可观测性则是功能无关但开发必需的工程旁路；从Agent承担的任务和用户需求来看，这三者构成了一个可交付智能软件项目的基础底座。
### 上下文工程
重要的原则：保护前缀缓存

如何设计系统提示词？

如何动态更新上下文？append-only为主要原则

如何压缩上下文？工具调用大结果落盘（实践为50000字符），只返回头部预览，有需要再查；压缩时，在原上下文后追加压缩指令（利用前缀缓存），生成摘要压缩，拼接上最近几轮对话历史，替换掉上下文中的对话历史部分（系统提示词、工具描述等静态部分不变）

### 评估体系
AGENT评测目前没有金标准，尤其是针对不同业务的AGENT，依赖业务场景和专家人工构建专门指标体系进行评测。
我们考虑编码场景的能力评测和工具调用通用能力，重点看编码任务的：pass@1,执行步数，token开销；看工具调用能力的准确性、步数。
SWE-bench-lite测评操作见[[docs\mewcode设计文档\给你的Agent跑一次真实评测.md]]

除了SWE-bench-lite，用来测试代码场景。我觉得还可以增加工具调用能力的评估测试：
- BFCL (Berkeley Function Calling Leaderboard)
- ToolBench
- τ-Bench (Tau-bench)
